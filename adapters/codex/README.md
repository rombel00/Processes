# Processes в Codex — адаптер 0.3.0

P2 принят; актуальная корректировка навигации и стоимости —
[пакет](../../docs/plans/risk-based-block-workflow.md). Фактические проверки
и ограничения — в [связанном отчёте](../../docs/validation/risk-based-block-workflow.md).
Нужен Node.js 22 или новее. Сеть и дополнительные npm-пакеты установщику не нужны.

## Что делает владелец

В текущей задаче: «Подключи Processes из <папка исходника> к этому проекту».
Агент читает этот файл и [навык](process-workflow/SKILL.md), выясняет недостающее,
предлагает состав процесса, план и логику. Владелец принимает решения.
Агент выполняет команды, ведёт документы и Git в разрешённых границах.
Самостоятельно выбирать технический модуль или редактировать JSON не нужно.

После подключения достаточно описывать желаемый результат. При возвращении
агент читает состояние и либо продолжает согласованный пакет, либо предъявляет
следующее предложение. Приёмка результата и разрешение следующего этапа —
отдельные решения. Ручная команда на контрольной точке сохраняется.

Roadmap хранит крупные блоки самостоятельно принимаемого результата — например,
весь MVP. Агент сам определяет активные блок, часть и подблок и в первом
сообщении сообщает цель, фактическую и рекомендуемую модель с причиной.
Scope и фундамент обычно разделяют задачи; итерационная delivery может вести
несколько связанных подблоков подряд в одном чате. На DoD пакета агент
сохраняет handoff и предлагает новую задачу с готовым промтом.

Без глобального входа в новом проекте нужно указать исходник Processes один раз.
Глобальный вход описан ниже; он предлагает процесс, но не устанавливает его
в каждый проект и не обновляет ранее подключённые проекты молча.

## Что устанавливается

| Файл | Назначение |
| --- | --- |
| `AGENTS.md` | Короткий блок входа; существующий текст сохраняется |
| `.gitattributes` | Блок сохранения точных байтов методик/пакетов при Git checkout; старые правила сохраняются |
| `.agents/skills/process-workflow/SKILL.md` | Нативный навык Codex с name/description |
| `.process/vendor/plugins/…` | Зафиксированные копии только выбранных модулей |
| `.process/runtime/process.mjs` | Локальная проверка без исходного клона/сети |
| `.process/installation.json` | Версии, пути документов, контрольные суммы |
| `.process/connection*.json` | Предложение и запись реального согласия на него |
| `.process/state.json` | Текущий пакет, согласие и точка остановки |
| `docs/process/…`, `.process/status.md` | Паспорт, roadmap, журнал и состояние; существующие сохраняются |

Повторение **того же** подключения проверяет целостность и ничего не пишет.
Изменение модулей, версии или сопоставления документов требует отдельной миграции;
автоматического обновления с перезаписью нет. Пользовательский текст вне блока
AGENTS.md и содержимое проектных документов могут меняться без поломки установки.
Вендоренные методики редактируют в исходнике, не внутри конкретного проекта.

Codex загружает цепочку AGENTS.md от корня репозитория к рабочей папке;
`AGENTS.override.md` имеет приоритет. Поэтому установщик отказывается работать
при корневом override. Вложенные инструкции и глобальный лимит загрузки нужно
проверять в фактической сессии: doctor не моделирует всю конфигурацию Codex.
См. [официальное описание AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
и [навыков](https://learn.chatgpt.com/docs/build-skills).

## Команды для агента

Запускать из клона Processes. Пути с пробелами заключать в кавычки.

```sh
node scripts/process.mjs inspect --project /path/to/project
node scripts/process.mjs apply --project /path/to/project --proposal /path/to/proposal.json --approval /path/to/approval.json
node scripts/process.mjs doctor --project /path/to/project
# После установки исходный клон не требуется для проверки:
node .process/runtime/process.mjs doctor --project .
node .process/runtime/process.mjs handoff --project .
```

`inspect` ничего не меняет, выводит найденные точки входа. Это не автоматическое
интервью с регулярными выражениями: агент читает контекст, задаёт вопросы и
применяет единую таблицу из WORKING_AGREEMENT. Исполнительная команда не делает
вид, что умеет понять цель или получить согласие без разговора.

Предложение готовит агент **до согласования**; например, для исследования:

```json
{
  "schema": 1,
  "revision": "connection-r1",
  "sourceSha256": "Хэш исходника из результата inspect",
  "goal": "Сравнить варианты по подтверждённым источникам",
  "modules": ["process-core", "product-discovery"],
  "reasons": {
    "process-core": "Согласования, дорожная карта и восстановление",
    "product-discovery": "Есть конкретные неизвестные факты для исследования"
  },
  "documents": {
    "profile": "docs/process/PROJECT_PROFILE.md",
    "roadmap": "docs/process/ROADMAP.md",
    "approvals": "docs/process/APPROVALS.md",
    "status": ".process/status.md"
  }
}
```

Можно сопоставить существующие Markdown-документы под `docs/`; установщик их
не меняет. Новые создаются из шаблонов P1. Агент заполняет их реальными решениями
в рамках согласованного подключения. Пустые шаблоны не означают готовности.
`inspect` возвращает хэш комплекта исходных методик и адаптера. Агент включает
его в предложение до согласования. Если исходник изменился, apply откажет,
даже когда номера версий сохранились. При запуске inspect не из исходника
передайте `--source /path/to/Processes`. Это не проверка подписи поставщика:
источник выбирается и проверяется агентом в согласованном пакете.

После реального согласия агент сохраняет отдельный approval.json:

```json
{
  "schema": 1,
  "kind": "connection",
  "decision": "approved",
  "date": "YYYY-MM-DD",
  "source": "Ссылка/идентификатор реального сообщения владельца",
  "quote": "Точные слова владельца",
  "sha256": "SHA-256 точных байтов proposal.json"
}
```

Пример — схема, не разрешение установки. SHA можно получить через PowerShell
`(Get-FileHash -Algorithm SHA256 proposal.json).Hash.ToLowerInvariant()`.
Изменение даже перевода строки меняет байты: сохраните утверждённый файл,
не переписывайте его после согласования. Историю approval храните, не заменяйте.

## Активный пакет и контрольная точка

По умолчанию `.process/state.json` содержит `phase: awaiting-package`.
После предъявления и согласования конкретного пакета агент записывает:

```json
{
  "schema": 1,
  "phase": "ready",
  "package": "docs/process/packages/P1.md",
  "approval": "docs/process/approvals/P1-r1.json"
}
```

Запись согласия имеет ту же схему, `kind: package`, хэш байтов файла пакета.
В журнале APPROVALS.md оставить человекочитаемую запись и ссылку на JSON.
Пакет содержит план, логику, DoD, модель/задачу, проверки, разрешённые действия
и checkpoint по шаблону P1. После исполнения `phase: checkpoint`; сам пакет
не меняется, результат и доказательства идут в status/отчёт. Новое согласие
на следующий пакет не стирает старое. Не редактируй state ради обхода остановки.

```sh
node scripts/process.mjs check-approval --document docs/process/packages/P1.md --approval docs/process/approvals/P1-r1.json --kind package
```

Doctor проверяет хэши, состав/версии, инструкции, наличие документов и актуальность
согласия активного пакета. При ошибке exit 1; корректная остановка — exit 0
с `phase: checkpoint` и сообщением STOP. Это две разные ситуации.
Он **не** проверяет личность автора записи, семантику плана, полномочия в GitHub
или разрешение на прод. Права сервера/CI — отдельная работа P3/P4.

`handoff` (>=0.2) — read-only индекс для реальной передачи в новую задачу или
длительной паузы: результат doctor,
пути и SHA-256 управляющих документов/активного пакета. При неверном согласии
возвращает ошибку и `next: blocked`; на checkpoint — только обсуждение
следующего узла. `ready` предлагает прочитать допуск, не даёт новый.
Команда не пересказывает документы и не проверяет смысл дерева: агент читает
status и активные блок/часть/подблок roadmap. Она не нужна после каждого внутреннего шага;
узел/родитель не дублируются отдельным JSON-графом.

## Глобальный вход и обновления

Для локального Codex: короткие общие правила в пользовательском AGENTS.md и
навык `process-entry` из этого адаптера в доступном каталоге пользовательских
skills. Рядом с установленным навыком `source.md` указывает абсолютный путь
рабочего исходника Processes. Перед изменением сохраняются прежние настройки;
существующий текст AGENTS не заменяется. При конфликте override — сначала разбор.

Глобальный вход маршрутизирует в установленную версию проекта, если она есть;
иначе — в исходник для обсуждения подключения. Он не вендорит модули заранее.
Изменения исходника доступны новым подключениям после проверки/согласования;
установленные проекты остаются на зафиксированных копиях. На старой версии
использовать её runtime; исходный doctor 0.2 не является мигратором для 0.1.
Уже начатая сессия может не перечитать глобальные инструкции — обнаружение
нужно проверять в новой задаче, не обещать ретроактивное включение.

Объединять roadmap и предметные методы не нужно: roadmap хранит крупные блоки,
их части/подблоки и зависимости, текущая карточка определяет исполнение, status —
передачу. В начале задачи видны блок/часть/подблок, цель/DoD, фактическая и
рекомендуемая модель с причиной, проверенные папка/worktree, репозиторий, ветка/HEAD,
рабочие изменения, окружение и STOP. На выходе эти ориентиры входят в передачу
вместе со следующим рекомендуемым узлом, моделью и готовым сообщением.
Это короткий паспорт старта, не новый документ; подробнее — WORKING_AGREEMENT §3.
Каждый STOP пакета дополнительно показывает «Что дальше» и готовый промт;
внутренний шаг той же delivery оставляет только компактную запись прогресса при
`state.phase: ready`.
Источник последовательности — roadmap по пути manifest (до подключения — по
согласованному сопоставлению/реестру) и связанный предметный plan/пакет; status
только хранит позицию и ссылки. Нет сохранённого продолжения —
следующий чат планирует его или принимает родительский DoD, а не исполняет
выдуманный шаг.

## Сохранность, Git и восстановление

- Установка предварительно проверяет все пути и отказывается затирать чужие
  служебные файлы. Symlink/junction, абсолютные и выходящие пути запрещены.
- При обычной ошибке записи восстанавливает AGENTS.md/.gitattributes и убирает созданное.
  При аварийном завершении процесса/сбое диска может остаться частичная установка;
  marker пишется последним, doctor обнаруживает проблему. Не заявляется
  транзакционность против отключения питания или конкурентных записей.
- Перед первым изменением AGENTS.md и .gitattributes копируются в
  `.process/backup-before-connection/`. После ошибки сначала сохранить
  оставшиеся файлы и изучить diff; не удалять `.process` целиком.
- Коммитить AGENTS.md, .gitattributes, `.agents/skills/process-workflow`, runtime/vendor,
  installation/connection/state и проектные документы. В старых проектах
  `.process/*` может игнорироваться: агент проверяет `git check-ignore` и явно
  предлагает корректировку; установщик сам не меняет .gitignore и не коммитит.
  Резервную копию AGENTS.md коммитить необязательно; секретов в инструкциях быть не должно.
- Утверждённые пакеты хранятся в `docs/process/packages/`; Git не преобразует
  в них переводы строк. Это сохраняет хэши при переносе между Windows/Linux.
  Более глубокие пользовательские .gitattributes могут переопределить правило;
  после checkout doctor обязательно повторяется.
- Для отката изучить diff и восстановить только файлы подключения из Git/backup,
  сохранив новые решения/документы. Автоудаления и глобальной активации нет.

```sh
node --test tests/process.test.mjs

```

Claude-путь остаётся прежним marketplace. Его инструкции в Codex используются
как методики, а не регистрируются с несовместимыми frontmatter/tools/model.

отдельным пилотом; P2 проверяет подключение, восстановление и остановки.

## Маршрут, модель и передача

Для нового запроса сначала укажите `work_type`, `execution_mode`, доказательства
и риск: `commercial_hypothesis`, `business_request`,
`existing_product_change` или `personal_utility`; режим — `explore`,
`experiment`, `build` или `high_risk`. Коммерческий маршрут не создаёт roadmap
разработки, пока нет решения на основе заранее указанного порога.
Короткий практический вход и примеры — в [OWNER_PLAYBOOK](../../OWNER_PLAYBOOK.md).

Sol/high ведёт неоднозначную постановку, архитектурные развилки и интеграцию;
Terra/high выполняет локальную обратимую дельту по принятой спецификации;
Sol/high делает обычное независимое ревью; Astra/high — high-risk
architecture/security и финальный аудит. Terra не является единственным
ревьюером. На DoD/STOP передайте ветку/commit, проверки, ограничения, следующий
узел и готовый промт; новый чат требуется для реальной передачи, а не для
каждого внутреннего шага.
