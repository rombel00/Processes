# processes

Claude Code plugin marketplace с общими процессуальными скиллами для всех моих
проектов: от продуктового ресерча до разработки и запуска.

> **Идёт пересборка в единую систему.** Контракты — в
> [`ARCHITECTURE.md`](ARCHITECTURE.md), карта фаз и артефактов — в
> [`PROCESS.md`](plugins/process-core/PROCESS.md), решения по каждому скиллу — в
> [`INVENTORY.md`](INVENTORY.md), источники — в [`SOURCES.md`](SOURCES.md),
> известные пробелы — в [`GAPS.md`](GAPS.md), шаблоны — в [`templates/`](templates/).
>
> Каркас готов, плагины наполняются. Ниже — то, что уже работает.
>
> **Версия 2 процесса.** Всегда полный путь, без глубин «бриф и сразу код» /
> «только хребет» — ни один гейт не выключается по масштабу продукта.
> Единица работы delivery — эпик, не релиз целиком. Подробности —
> [`PROCESS.md`](plugins/process-core/PROCESS.md).

## Когда НЕ ставить этот marketplace

Полный путь — не для всего, что ты делаешь. Это не глубина внутри процесса
(её больше нет, см. выше) — это развилка **до** него: решение, идёт ли
проект в процесс вообще, а не насколько облегчённо он там пойдёт.

Признаки, что процесс избыточен — быстрый скрипт/бот/поделка, не продукт:

- Деньги, PII, авторизация и доступ к чужим данным не участвуют.
- Пользователь один — ты, и результата ошибки не увидит никто, кроме тебя;
  ошибка дешёвая и сразу заметна (бот выдал ерунду — заметил, поправил), не
  требует ни отката, ни расследования.

**Это решающая пара — она про цену ошибки, а не про размер или возраст
поделки.** Два признака ниже сами по себе ничего не решают, это только повод
не гадать и спросить владельца явно, если неочевидно:

- Продукт живёт недолго и правится разово — тогда точно не нужна
  устойчивость к тому, что через паузу к нему вернётся холодный агент без
  памяти диалога. Живёт месяцами как персональный инструмент — это само по
  себе процесс всё ещё не включает, если решающая пара выше держится: заведи
  себе заметки/README вручную, раз работаешь с Клодом напрямую, это не
  задача этого marketplace.
- Ты сам ведёшь пару-программирование с Клодом в моменте, а не отправляешь
  задачи в отдельные сессии/субагентов, где тебя рядом нет — тоже сигнал о
  трении (субагенту в чистом контексте нужны свои заметки для продолжения),
  не о цене ошибки.

Если так — просто работай с Claude Code напрямую, без этого marketplace.
Пример: бот, который раз в день собирает популярные статьи из телеграм-каналов
и работает у тебя одного месяцами, местами через отдельные сессии — один
пользователь, ошибка дешёвая, денег/PII/авторизации нет. Полный Definition →
Delivery здесь стоит на порядок дороже самой задачи, даже если бот уже
прожил полгода.

Решающий тест — деньги/PII/авторизация/доступ к чужим данным, несколько
пользователей, или ошибка, которую дорого либо долго распутывать (нужен
откат, расследование, не видно сразу). Хотя бы один из этих признаков — ставь
процесс целиком, без исключений: `orchestrate` (`plugins/process-core/skills/orchestrate/SKILL.md`,
Шаг 0) один раз спросит явно, если это не очевидно с самого начала, и
запомнит ответ — не будет переспрашивать каждую сессию. Решение
пересматриваемо в обе стороны по факту, не только вверх (`orchestrate`,
«Триаж», «Пересмотр» и «Пересмотр вниз»; причины — `GAPS.md`).

## Плагины

### `process-core` — ставится всегда

Ядро процесса. Здесь же лежит
[карта фаз и артефактов](plugins/process-core/PROCESS.md) — она внутри плагина,
потому что читается в репозитории продукта.

- `orchestrate` — где продукт в процессе, что дальше, чего не хватает на входе;
  ведение пар producer → reviewer, лимит циклов, блокеры, `status.md`.
- `independent-review` — независимое ревью документа или кода отдельным
  субагентом перед тем, как зафиксировать шаг как готовый. Для того, у чего
  нет своего гейта.

### `product-definition` — хребет продуктовой работы

- `brief-writing` — структурированное интервью для продуктового брифа, по
  фиксированному чек-листу.
- `lean-canvas` — бизнес-модель продукта на одной странице.
- `user-story-mapping` — ведёт весь Definition: путь пользователя целиком →
  эпики и скоуп релиза (плюс визуальный концепт и информационная
  архитектура на весь продукт) → детальная проработка каждого эпика по
  очереди (сценарии, эдж-кейсы, вайрфреймы), с личным согласованием
  владельца на каждом шаге.
- `retro` — что узнали после релиза; спрашивает владельца, что дальше
  (свой скоуп или RICE-скоринг бэклога), не возвращает процесс в `frame`
  автоматически.
- Независимые ревьюеры на каждом гейте: `brief-reviewer`, `story-map-reviewer`
  (по эпику, не по всей карте разом).

### `product-discovery` — опционально

- `market-research` — рынок, конкуренты, провалившиеся кейсы, тренды,
  возможности для дифференциации.
- `persona-generation` — детальные профили пользователей: primary, secondary,
  anti-persona, early adopter.
- `persona-interview` — симуляция custdev-интервью с персоной, вердикт
  «купил бы / нет» и незакрытые возражения.

### `delivery` — опционально

- `architecture-design` — техническая архитектура в двух режимах: фундамент
  один раз на продукт, надстройка на каждый эпик — с обязательной сверкой
  на противоречия и чек-листом безопасности.
- `architecture-repair` — точечная починка архитектуры по замечаниям.
- `epic-prep` — готовит проработанный эпик к разработке: технадстройка +
  нарезка на задачи с полной спецификацией каждой (заменяет прежние
  `handoff-spec` и `task-planning`).
- `implementation` — код и тесты по одной задаче, с правилом «доказательство,
  а не просто зелёный тест». Запускается субагентом (не в основной сессии
  владельца) — существенную задачу доводит до вердикта `code-review` сразу
  и по отдельности, рутинную копит в сводное ревью перед концом эпика.
- `implementation-repair` — точечная починка кода по замечаниям код-ревью.
  Тоже субагент, вызывается `implementation`, не владельцем напрямую.
- `launch-check` — последняя проверка перед выпуском релиза: доказаны ли
  критерии приёмки эпиков, готовность отката, и что реальная выкатка
  (домен, хостинг) сделана, не только запланирована.
- Независимый ревьюер `handoff-reviewer` — проверяет `plan`, результат
  `epic-prep`.

### `product-design` — опционально, но обычно ставится вместе с `product-definition`

Вызывается изнутри `user-story-mapping` — не отдельная фаза после
Definition, а часть проработки: концепт и IA на этапе B, экраны по эпику
на этапе C. Не нужен только продуктам совсем без UI (API, CLI).

- `wireframe-spec` — текстовые Unicode-вайрфреймы экранов одного эпика.
- `information-architecture` — sitemap, инвентарь экранов, навигация, user
  flows на весь продукт целиком; по умолчанию сама предлагает разбор
  точек трения в пути к главной цели (journey map) разделом этого же
  документа.

### Появится позже

`legal` — контента по-прежнему нет ни в одном источнике. Каталог заводится
вместе с содержимым, не заранее.

## Как подключить в проекте

В `.claude/settings.json` проекта:

```json
{
  "extraKnownMarketplaces": {
    "processes": {
      "source": {
        "source": "github",
        "repo": "rombel00/processes"
      }
    }
  },
  "enabledPlugins": {
    "process-core@processes": true,
    "product-definition@processes": true,
    "product-discovery@processes": true,
    "product-design@processes": true,
    "delivery@processes": true
  }
}
```

Обязателен только `process-core` + `product-definition`. Остальное — по
продукту: `product-discovery` можно не включать (без него процесс идёт, а
выводы, которые опирались бы на рыночные данные, помечаются допущениями),
`product-design` — если нужен визуал, `delivery` — если дальше `frame` дело
дойдёт до кода.

При открытии проекта Claude Code предложит установить marketplace и плагины
автоматически.

## Как подключить в облачных/веб-сессиях (вендоринг)

Способ выше опирается на `github`-источник — это работает в локальном
Claude Code CLI, но не гарантированно в облачных/веб-сессиях: `~/.claude`
там никогда не доступен (у каждой такой сессии чистый контейнер), а
поведение автофетча по `github`-источнику при сбое доступа к
`rombel00/processes` нигде не документировано (тихий отказ или блокирующий
промпт — неизвестно), и объём доступа сессии к чужим репозиториям может
быть уже, чем у аккаунта в целом. Если продукт будет работать в облачных
сессиях — не полагайся на автофетч, вендори маркетплейс целиком в
репозиторий продукта:

1. Скопировать в репозиторий продукта (например, `vendor/processes/`)
   `.claude-plugin/marketplace.json` и весь каталог `plugins/` целиком —
   не отдельные файлы скиллов, не сплющивая в `.claude/skills/`.
   `${CLAUDE_PLUGIN_ROOT}` резолвится только внутри структуры плагина;
   россыпь файлов без обёртки ломает все кросс-плагинные ссылки (например
   `$(dirname "${CLAUDE_PLUGIN_ROOT}")/process-core/PROCESS.md`).
2. В `.claude/settings.json` продукта подключить вендоренный путь как
   источник `extraKnownMarketplaces` локальным путём. Подтверждено
   вживую (`claude plugin marketplace add ./vendor/processes`): ключ —
   `{"source": "directory", "path": "./vendor/processes"}`, не `"local"`
   и не `"dir"`.
3. `enabledPlugins` — та же секция, что и в примере выше, но **этого
   недостаточно**: `enabledPlugins` в `settings.json` сам по себе не
   ставит плагин в кэш `~/.claude/plugins/cache`, автоустановка на его
   основе не срабатывает. Нужен явный `claude plugin install
   <name>@processes -s project` — и в облачной сессии выполнять его
   вручную негде, контейнер чистый на каждом старте. Решение —
   `.claude/hooks/session-start.sh`, который на старте каждой сессии сам
   идемпотентно прогоняет `marketplace add` + `install` по всем нужным
   плагинам из вендоренной копии, без обращения к сети. Проверено на
   симуляции чистого контейнера (`~/.claude/plugins` обнулён) — все
   плагины встают через хук без сети.

Цена: обновления `rombel00/processes` не долетают до продукта
автоматически — при следующих правках процесса вендоренный
`vendor/processes/` нужно скопировать заново вручную.

Та же схема применима к любому другому маркетплейсу скиллов (например
`rombel00/game-processes`) — свой подкаталог в `vendor/`, своя запись в
`extraKnownMarketplaces`.
