# Предметная маршрутизация и delivery-гейты

Читать только при работе с соответствующей фазой полного продуктового маршрута.
Все переходы ниже ограничены пакетом и деревом задач из WORKING_AGREEMENT §3.
Названия `Agent` и producer-субагентов относятся к Claude; Codex использует
свой адаптер и может исполнять шаг в основном контексте с отдельным ревьюером.

## Шаг 1. Определить, где мы

**В чек-листе фаз производная только часть «файл есть».** Отметка
«утверждено» — данные о пройденном гейте, не выводятся заново пересканом
`docs/`: доказательство (отчёт ревью) — законно одноразовый `scratch`.
Понижай «утверждено» только по позитивной улике — артефакт правился после
отметки, или владелец сам сказал, что гейт не проходили — **и только
внутри одного и того же блока эпика**: у каждого `<task-id>` в списке
«Definition, этап C» и в списке «Delivery» своя область действия правила
(это два разных списка, не один — `PROCESS.md`, «Состояние пайплайна»), у
«Фазы — продукт» — своя. Текущие открытые вопросы — тоже не производная
(`status.md` — `committed`).

**Следующий эпик Definition C не начат, пока предыдущий не согласован
владельцем и не прошёл `story-map-review`** (`PROCESS.md`, «Правила
движения» п.4) — блок следующего `<task-id>` в списке Definition C
`status.md` заводится пустым только в этот момент, не раньше. Это не то
же самое, что закрытие эпика в Delivery — два разных списка блоков (см.
«Состояние пайплайна» в `PROCESS.md`).

1. Прочитай `.process/status.md` — он в git, должен быть, если работа уже
   начата.
2. Проверь входы текущего пакета и зависимые блоки эпиков скоупа в
   `docs/product/` и `docs/delivery/`; не читай все документы продукта заранее.
   Строки нет, а каталоги в `docs/delivery/` есть — не гадай по дате
   изменения, спроси владельца один раз и допиши строку.
3. Чек-лист фаз разошёлся с тем, что нашёл, — почини его и скажи, что чинил.
   Открытые вопросы не трогай без явного основания — это чужие записи, не
   кэш. **Явное основание есть, когда владелец в диалоге отвечает на
   конкретный открытый вопрос** — тогда вычеркни строку сразу, коротко
   указав, чем закрыт.

Сверь версии входов и результата с записью проверки/допуска. Автоматического
механизма в P1 нет — проверяй вручную по commit или редакции. Совпадение
пути файла не доказывает актуальность проверки. Для старого согласия без
версии не придумывай commit; при сомнении предъяви различия владельцу.

## Шаг 2. Сказать, что дальше

**Если следующая фаза — продюсер, которого может замещать доменный пак**
(Definition) — проверь замещение, иначе пропусти этот пункт целиком.
Установленные плагины лежат рядом с твоим: `"$(dirname "${CLAUDE_PLUGIN_ROOT}")"`.
Проверяй оттуда: `grep -rln '^replaces:' "$(dirname "${CLAUDE_PLUGIN_ROOT}")"/*/skills/*/SKILL.md`.
Прежде чем называть найденный пак, сверься с `enabledPlugins` в
`.claude/settings.json` продукта или спроси владельца. Ничего не нашёл
(пустой результат `grep`) — молча называй универсальный скилл, это штатный
случай, пока в marketplace нет ни одного доменного пака.

**Команда упала или каталог не открылся** (не то же самое, что пустой
результат) — скажи владельцу прямо, что проверить замещение не удалось.

Назови следующий разрешённый пакет и проверь его входы по реестру. Таблица
ниже выбирает предметную методику, но не даёт разрешения её запускать.
Для каждого нового этапа представь план/логику, DoD, проверки, модель и
задачу, затем получи согласие. Ревью и исправления внутри уже согласованного
пакета выполняй без повторных вопросов в пределах его лимитов.

| Ситуация | Что делаешь |
|---|---|
| Все входы на месте | Называешь фазу и скилл, который её закрывает |
| Нет обязательного входа | Называешь недостающий артефакт и фазу, которая его даёт |
| Нет опционального входа | Идём дальше. Напоминаешь пометить зависящие выводы допущениями |
| Definition, этап C — эпик согласован владельцем, но `story-map-review` не пройден | Гейт не пропускается — предложи его прежде, чем переходить к `epic-prep` (`PROCESS.md`, «Гейт не пропускается») |
| Definition, этап C — есть непройденное «Backbone/скоуп/эпик N — ждёт подтверждения владельцем» в открытых вопросах | Это блокер, не обычный шаг — реши его раньше, чем называть следующую фазу (`PROCESS.md`, «Владелец подтверждает поток до гейта») |
| Definition, этап C — в открытых вопросах есть «Конфликт эпика `<task-id>` с техническим фундаментом» (лёгкий чек нашёл несоответствие) | Блокер класса Б, не отложенная запись — не называй ни следующий эпик Definition C, ни `epic-prep` этого эпика, пока владелец не решит (`PROCESS.md`, «Технический фундамент») |
| Этап B закрыт (скоуп/концепт/IA подтверждены), Технический фундамент ещё не запущен или не утверждён | Следующая фаза — Технический фундамент (`architecture-design`, режим «Фундамент»), не этап C: он идёт перед C, не рядом с ним (`PROCESS.md`, «Технический фундамент») |
| Эпик прошёл `story-map-review`, но в чек-листе Definition C для него нет отметки ни «visual-design — утверждено», ни «пропущено владельцем» | Не называй `epic-prep` — предложи `visual-design` (или спроси владельца, пропускает ли он его явно) прежде, чем эпик уходит дальше (`PROCESS.md`, «Definition, этап C») |
| Эпик прошёл `story-map-review`, визуальный проход этого эпика утверждён или явно пропущен владельцем, Технический фундамент утверждён, у этого эпика ещё нет своего блока в списке Delivery `status.md`, и в шапке `status.md` нет строки «Эпики в работе параллельно» с этим `<task-id>` | `epic-prep` для этого эпика — предложи этот пакет после контрольной точки; параллельное исполнение требует отдельного разрешения |
| То же самое, но `<task-id>` уже есть в строке «Эпики в работе параллельно» | Не предлагай `epic-prep` — он уже отработал, эпик разрабатывается прямо сейчас в другой сессии (другой worktree); просто скажи об этом владельцу |
| Эпик прошёл `story-map-review`, но Технический фундамент ещё не утверждён | Delivery этого эпика не начата — фундамент нужен `epic-prep` на шаге 1; напомни, если фундамент ещё не запущен |
| По `test_report` видно, что все задачи эпика закрыты (у каждой заполнено «Проверено по коммит») и строка «Ожидает сводного ревью» пуста, ветка ещё не в `stage` | **Если слияние входит в согласованный пакет, слей ветку эпика в `stage` сам** (`git merge <task-id>`), тем же проходом, что отмечаешь эпик технически закрытым в `status.md` — это до ручного теста владельца, не после: `stage` и есть место, где он тестирует (`PROCESS.md`, «Эпик и git»). **Выполняй в дереве, где сейчас `stage`** — обычно не то дерево, где только что работал `implementation` (у него checked out `<task-id>`): если ты в дереве эпика, выполни команду с рабочим каталогом согласованного дерева stage. Если дерево занято другой работой, согласуй координацию; не переключай чужой HEAD. Остальные Git-действия также выполняет агент в границах пакета. **Если в `test_report` раздел «Визуальное состояние» не пуст — пришли сами файлы скриншотов владельцу** (`SendUserFile`), не только путь в документе, вместе с сообщением о готовности эпика: он не должен идти за ними в файловую систему сам. Эпик уходил в отдельную сессию — сними строку «Эпики в работе параллельно» тем же проходом |
| Все задачи `plan` эпика закрыты (у каждой заполнено «Проверено по коммит» в `test_report`), но строка «Ожидает сводного ревью» не пуста | Эпик не готов, вне зависимости от того, что показывает беглый скан — сводное ревью рутинных задач ещё не пройдено (`PROCESS.md`, «Значимость надстройки и задачи»). Не сливай ветку в `stage`, не предлагай ручной тест — вызови `implementation`: он остановится перед сводным ревью и вернёт список задач и диапазоны коммитов, доведи гейт до конца сам («Ведение пары producer → reviewer», раздел про `code-review`) |
| Эпик слит в `stage`, ручной тест владельца ещё не пройден | Предложи протестировать этот эпик на `stage`; предъяви результат пакета и STOP. Следующий эпик — отдельное предложение |
| Владелец на ручном тесте нашёл дефект, эпик-задача на починку закрыта и прошла `code-review` — на ветке эпика есть коммиты, которых ещё нет в `stage` (`git log stage..<task-id>` не пуст) | Слей повторно, тем же приёмом, что первый раз — это не разовое действие, а состояние, которое проверяешь каждый раз перед тем, как считать эпик снова готовым к тесту |
| Эпик закрыт в Delivery (все задачи, `code-review`, слит в `stage`, ручной тест владельца пройден), в скоупе есть следующий эпик, уже прошедший `story-map-review` | Предложи пакет `epic-prep` для него; до нового допуска остановись |
| Эпик закрыт в Delivery, следующий эпик скоупа ещё не прошёл `story-map-review` | Delivery ждёт — предложи продолжить Definition C для него, если это ещё не идёт в другой сессии |
| Все эпики скоупа реализованы, слиты в `stage` и протестированы | `launch-check`: сначала readiness, затем отдельное согласие на точную версию, выкладка и проверка. До допуска merge/deploy запрещены |
| `learn` не пройден | Не пропускай молча — `retro` доступен явным вызовом, спроси владельца, хочет ли он его сейчас |
| Фаза без своего гейта (`discovery`, `strategy`) | У неё нет ревьюера по конструкции — не предлагай завести. Сомневается владелец в конкретном результате — есть `independent-review` |

**Definition, этап C уже «в процессе» на эпике `<task-id>`** — не начинай
следующий, пока текущий не согласован владельцем и не прошёл
`story-map-review` (`PROCESS.md`, «Definition, этап C»). Другой пакет Delivery
может стартовать одновременно только при явном разрешении параллельности.

**`implementation` уже «в процессе»** — `plan` не несёт своего состояния,
называть саму фазу недостаточно. Сверь `plan` с разделом «История по
задачам» в `test_report` (если он есть) и назови конкретную незакрытую
задачу.

**Если делегирование включено в согласованный пакет, `implementation` запускается субагентом.**
Нет разрешения или инструмента — предложи способ выполнения/ревью и останови
зависимую работу; не запускай агента лишь из-за выбранного модуля. В
отличие от остальных продюсеров, `implementation` — субагент
(`plugins/delivery/agents/implementation.md`): через `Agent`, явно передав
пути к `plan`, `architecture`/`wireframes` (если есть), `<task-id>` и
конкретную незакрытую задачу. У субагента, вызванного через `Agent`, нет
доступа к `Agent` — гейт `code-review` он провести не может физически
(`agents/implementation.md`, «У тебя нет доступа к `Agent`»): реализует
задачи подряд и останавливается перед ближайшим гейтом — сразу после
коммита существенной задачи, или перед сводным ревью на последней задаче
эпика — одним вызовом покрывая столько рутинных задач, сколько наберётся
до этой точки, не обязательно весь эпик.

**Получил `status: "done"` с полем `ready_for_review`** — это стоп на
гейте, не готовый эпик. **Прежде чем звать `code-reviewer` — отметь это в
`status.md`**, в блоке эпика под Delivery: `- [ ] implementation — задача
1.3 на code-review (цикл 1 из 2)` (или «на сводном code-review» — для
режима «Свод»). Это не для галочки: счёт цикла лимита иначе нигде не
хранится, и без этой строки обрыв сессии посреди гейта неотличим от
обрыва самого `implementation` (см. ниже, «Что-то оборвалось»). Веди цикл
сам: `code-reviewer` на переданный диапазон → при `rework` —
`implementation-repair` → повторный `code-reviewer` (перед каждым новым
проходом обнови номер цикла в этой же строке) → как только вердикт
устоялся (`approved`, или лимит исчерпан с одними некритичными находками)
— верни строку к `- [ ] implementation — в процессе`, и только теперь
вызови `implementation` заново тем же путём, передав ему этот вердикт
(путь к отчёту, `reviewed_commit`, номер задачи или список задач свода);
он сам впишет «Ревью», «Проверено по коммит» и «Принятый долг» в
`test_report` и продолжит со следующей задачи. Подробный порядок —
«Ведение пары producer → reviewer» ниже, раздел про `code-review`.

**Получил `status: "done"` без `ready_for_review`** — незакрытых задач и
гейтов, ожидающих прохождения, в `plan` больше нет: эпик готов. Скажи
владельцу: эпик готов к проверке. Сверь DoD пакета, сохрани передачу и
остановись. Следующий эпик только предложи, не запускай.

**Получил `status: "blocked"`** — эскалация владельцу, как обычно
(`PROCESS.md`, «Блокеры и эскалация»); не пытайся продолжить цикл гейта
сам.

**Что-то оборвалось посреди эпика** (сессия закрылась или любой вызов
упал технически, не вернув ни `done`, ни `blocked`) — это штатный ход, не
поломка эпика, но сначала сверься со строкой блока эпика в `status.md`,
не с тем, кто именно упал — она и решает, что оборвалось на самом деле:

- **Строка простая, `implementation — в процессе`, без пометки про
  code-review** — упал сам `implementation` (или ты его ещё не успел
  вызвать). Перезапусти его через `Agent`, передав ту же незакрытую
  задачу. Последняя запись в «Истории по задачам» `test_report` без
  «Проверено по коммит» — ожидаемый след, не задача-призрак: новый агент
  сам разберётся, доделать код или запросить гейт заново
  (`implementation`, «Закрыта =»), это не твоя часть работы.
- **Строка несёт пометку «на code-review (цикл N из …)»** — оборвался не
  `implementation` (он уже отдал `ready_for_review`, звать его заново
  рано), а цикл гейта, который вёл ты. Проверь диск на ожидаемом пути
  отчёта (`.process/<task-id>/code_review_<X.Y>.md`, или `_sweep.md` для
  свода): отчёт есть и несёт вердикт по существу — продолжи цикл с этого
  вердикта (на починку, или уже к вызову `implementation` для записи);
  отчёта нет — запусти `code-reviewer` на тот же диапазон с тем же
  номером цикла, что в строке (обрыв не должен списывать цикл, которого
  по факту не было). Оборвался сам `implementation-repair`, не вернув ни
  `done`, ни `blocked`, — тот же приём: перезапусти его через `Agent` с
  теми же путями к отчёту ревью, номер цикла не трогай.

**После `learn`, если владелец назвал новый скоуп** — следующая фаза не
`frame`, а технический фундамент (сверка/расширение), затем Definition,
этап C для новых эпиков (`PROCESS.md`, «Launch и Learn»). Путь (этап A)
пересматривается только по явному решению владельца.

## Ведение пары producer → reviewer

Полное правило — «Пара producer → reviewer» и «Гейты» в `PROCESS.md`. Читай
его там, здесь только твоя часть: куда направить вердикт.

**Запуская ревьюера, передай ему всё явно**: путь к артефакту, путь к
`PROCESS.md`, и `<task-id>` из «Текущий эпик» `status.md`, если гейт
delivery-трека или `story-map-review` конкретного эпика.

| `verdict` | Действие |
|---|---|
| `approved`, находок нет | Записать проверенную версию и вердикт. На контрольной точке — результат и стоп; следующий этап требует допуска |
| `approved`, но остались некритичные находки (с первого круга или после лимита циклов — не важно, какого) | **Ты не правишь committed-документы сам.** Верни находки продюсеру (или repair-скиллу) с поручением перенести остаток в «Принятый долг» самого артефакта. Только после этого — «Фаза закрыта» |
| `rework` | На починку — см. ниже, кому именно |
| `blocked` | Эскалация владельцу |

**Кому отдавать починку.** По умолчанию — самому продюсеру. Исключение:
`architecture` и код чинит отдельный repair-скилл/субагент.

Следи за лимитом своего гейта — **1 или 2, зависит от гейта**
(`PROCESS.md`, «Лимит циклов»: продуктовые гейты, где владелец уже был
проверкой, — 1; технические, где независимый ревьюер единственная защита,
— 2). Если гейт вёл сам продюсер в своей сессии (`PROCESS.md`, «Правила
движения» п.2) — счёт вёл он; здесь досчитывай только то, что не
досчитано.

### `code-review` — та же таблица, но продюсер не сдаёт готовый артефакт

`implementation` останавливается перед этим гейтом, не дойдя до конца
`plan` (`agents/implementation.md`, «У тебя нет доступа к `Agent`») — ты
ведёшь весь цикл сам, тем же приёмом, что и для любого другого гейта
выше, с четырьмя отличиями:

- **База и диапазон диффа** — не «весь артефакт», а `diff_base`/`diff_head`
  (или список пар для свода) из поля `ready_for_review`, которое вернул
  `implementation`. Передай их `code-reviewer` как есть, не пересчитывай.
- **Чинит `implementation-repair`** (`PROCESS.md`, «Кто чинит»), и он тоже
  гейт сам не ведёт — доведя починку до диффа, готового к повторному
  ревью, останавливается и возвращает свой `ready_for_review` вместе с
  `mode`/`task`; повторный `code-reviewer` на этот диапазон запускаешь
  снова ты, не он — передай ему то же `mode`/`task`, что вернул
  `implementation-repair` (он же пишет отчёт в файл, названный по этому
  номеру, «Результат»).
- **В режиме «Свод» — сохрани некритичные находки первого круга сам,
  до того как звать `code-reviewer` второй раз.** Второй проход
  ревьюит только делту починки (`code-reviewer`, «Режим "Свод"»), не всю
  пачку заново, и **перезаписывает тот же файл отчёта** — 🟡-находки
  первого круга по задачам, которые чинить не пришлось, физически не
  попадут во второй отчёт и файл первого будет уже не прочитать. Если
  такие были — сохрани их в scratch-записи цикла до повторного ревью и добавь к
  вердикту, который в итоге передашь `implementation` (см. ниже): иначе
  «Принятый долг» этих задач останется пустым не потому, что находок не
  было, а потому что отчёт о них уже переписан.
- **«Фаза закрыта» здесь — не отдельное действие.** `test_report` —
  committed-документ с одним заявленным писателем (`implementation`), ты
  в него не пишешь. Как только вердикт устоялся (`approved`, или лимит
  исчерпан с одними некритичными находками) — верни строку `status.md` к
  `- [ ] implementation — в процессе` и вызови `implementation` заново,
  передав ему вердикт целиком: путь к отчёту ревьюера, `reviewed_commit`,
  номер задачи или список задач свода, **и некритичные находки прежних
  кругов, которые ты сохранил сам** (пункт выше), если они были — он сам
  впишет «Ревью», «Проверено по коммит» и «Принятый долг» в `test_report`
  и продолжит со следующей задачи (или скажет, что дошёл до конца `plan`).
  Лимит критичных находок после исчерпанного лимита циклов — не вызывай
  `implementation`, это не закрытая задача: эскалация владельцу, как в
  общей таблице.

Лимит цикла у `code-review` — тот же счёт **2**, что и у остальных
технических гейтов, но начинаешь его с нуля на каждую новую существенную
задачу и отдельно на каждый новый свод рутинных — не один общий счёт на
весь эпик (`PROCESS.md`, «Лимит циклов»).
