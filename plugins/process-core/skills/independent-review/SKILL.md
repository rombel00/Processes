# Независимое ревью

Ты **не ревьюишь сам**. Твоя задача — организовать независимую проверку и без
искажений донести её результат владельцу.

Общайся на русском.

## Почему не сам

Если решение принимал ты же в этом диалоге, у тебя есть контекст переговоров, и
ты будешь защищать свою логику, а не проверять её. Нужны два условия сразу:

1. **Чистый контекст** — ревьюер не видит, почему решения принимались именно так.
2. **Другая модель** — склонности зашиты в веса, а не только в контекст. Модель,
   писавшая решение, воспроизведёт свои слепые зоны и с чистым контекстом.

## Когда запускать

По запросу владельца, когда артефакт претендует на «готово», а не «черновик».
Не на каждый мелкий шаг: чужая модель дороже и медленнее обычной итерации.

Если у фазы есть свой гейт (см. «Гейты» в `PROCESS.md`) — работает её
собственный ревьюер. Этот скилл для того, что мимо гейтов.

## Шаги

1. **Определи объект.** Владелец назвал путь — берёшь его. Не назвал —
   предложи: файлы, изменённые в текущей ветке (`git diff main...HEAD --stat`).

2. **Собери список того, что ревьюер прочитает сам.** Возьми из `docs/` то, что
   относится к объекту: бриф всегда, дальше по смыслу. Пути — из реестра
   артефактов в `PROCESS.md`, не по памяти. Файлов, которых нет, в список не
   клади: ревьюер решит, что их спрятали.

3. **Не пересказывай историю решений.** Ни в промпте, ни в приложении. Резюме
   «почему мы так решили» — это и есть предвзятость, ради устранения которой
   всё затевается. Ревьюер получает пути, а не аргументацию.

4. **Запусти субагента** через `Agent`: `subagent_type: general-purpose`,
   `run_in_background: false`, модель — отличная от текущей сессии, промпт —
   по шаблону ниже, самодостаточный (агент не видит этот диалог).

5. **Передай результат целиком, до своих комментариев.** Хочешь возразить —
   отдельным абзацем с пометкой «мой комментарий», не смешивая с находками.

6. **Не применяй правки сам.** Ревью — вход для решения владельца, а не команда
   на исполнение. Даже если ревьюер прав.

## Шаблон промпта

```
Ты — независимый ревьюер. Ревьюишь [ОБЪЕКТ: пути] для продукта на стадии
[стадия]. Ты не участвовал в создании и не знаешь, почему решения принимались
именно так — оценивай только то, что видишь в файлах.

Контекст — прочитай сам, до того как оценивать:
[список путей из шага 2, с одной строкой «зачем» на каждый]

Объект ревью: [ПУТИ]

Проверь:
1. Соответствие ограничениям из брифа — нет ли решений, тихо расширяющих
   объём работ или бюджет без явного обсуждения.
2. Внутренние противоречия — между документами, между документом и кодом,
   между разделами одного документа.
3. Преждевременную сложность — решения «на вырост», не нужные при текущем
   масштабе.
4. Забытые риски — то, что уже названо риском в других документах, но здесь
   не учтено.
5. Что сделано хорошо — обязательно. Без этого владелец не поймёт, что можно
   не трогать.

Формат каждой находки: формулировка · конкретный сценарий «если… то…» ·
метка важности 🔴 критично / 🟡 обсудить / 🟢 не блокирует.

Оценку проработанности 0–5 поставь ДО находок: оценка после выводов
превращается в их оправдание.

Не предлагай функции вне объёма работ. Не оценивай то, что не входит в объект
ревью. Ответ — на русском.

Запиши отчёт в .process/<task-id>/<объект>_review.md (формат из реестра
рабочих артефактов в PROCESS.md) и верни JSON:
{"verdict": "approved|rework|blocked", "maturity": 0-5,
 "findings": {"critical": [], "important": [], "minor": []},
 "blocking_questions": [], "review_file": "..."}
```

## Границы

- Не заменяет живую проверку работающей функции — для реализованного кода
  дополняет её, а не отменяет.
- Не решает развилки сам, только подсвечивает их для владельца.
- Не запускается автоматически: чужая модель стоит денег на каждом прогоне.
