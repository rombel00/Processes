# Процесс: фазы, артефакты, гейты

Карта жизненного цикла продукта — от идеи до выученного урока: фазы, что каждая
даёт, где стоят проверки, как классифицируются блокеры и как ведётся состояние.

Это **рабочий документ**: его читает скилл `orchestrate` и любой, кто ведёт
продукт по процессу. Правила разработки самих скиллов — отдельно, в
`ARCHITECTURE.md` репозитория процессов.

> Все пути в этом документе — пути **в репозитории продукта**, над которым идёт
> работа, а не в репозитории процессов.

> **Общий договор, process-core 0.9.4.** Сначала читать
> [общий договор](WORKING_AGREEMENT.md): интервью, выбор модулей,
> согласование плана и логики, последовательность, Git и допуск версии в прод.
> Он действует и при прямом вызове отдельного скилла. Карта ниже — полный
> продуктовый маршрут, применяемый в выбранных предметных модулях; она не
> является разрешением исполнять все фазы. История прежних решений — GAPS.

**Границы задач поверх фаз:** roadmap состоит из крупных блоков результата
(например, MVP или следующий релиз). Внутри блока идут тонкий scope, фундамент
архитектуры/безопасности, итерационная delivery по подблокам и совокупная
приёмка/релиз (WORKING_AGREEMENT §3). Карта ниже выбирает предметную методику,
а не требует чата на каждый внутренний шаг или подблок. Любое «дальше» означает
действия внутри текущего согласованного пакета. На DoD пакета — передача и STOP;
тесты, ревью и мини-задачи внутри разрешённой delivery не создают отдельную
пользовательскую задачу.
В Codex рабочая задача может сама исполнять выбранный шаг и звать отдельного
ревьюера; обязательность producer-субагента и ограничения инструмента `Agent`
ниже описывают Claude-упаковку, не возможности Codex.

## Карта

```
FRAME
  frame ── 🚪 brief-review
    │
    ▼
SCOPE БЛОКА
  A. путь ──── владелец подтверждает поток целиком
    │
    ▼
  B. путь → эпики, владелец режет скоуп релиза, каждому — свой task-id,
     визуальный концепт + информационная архитектура — на весь продукт
    │
    ▼
  (приняты границы, подблоки, общие потоки и архитектурно значимые ограничения;
   подробности каждого подблока ещё не обязательны)
    │
    ▼
  ФУНДАМЕНТ АРХИТЕКТУРЫ/БЕЗОПАСНОСТИ БЛОКА:
  фундамент или дельта к существующему 🚪 architecture-review
    │
    ▼
ИТЕРАЦИОННАЯ DELIVERY — подблоки идут последовательно; один пакет/чат может
  явно перечислить несколько связанных подблоков

  для каждого подблока:
  C. подробная спецификация + дизайн 🚪 story-map-review
    → impact check относительно фундамента
       без триггеров/вопроса: covered_by_foundation (local-no-trigger-check)
       есть вопрос/триггер: architecture-advisor (read-only)
       advisor может подтвердить covered_by_foundation
       delta_required: адресная дельта 🚪 architecture-review
    → epic-prep 🚪 handoff-review
    → разработка и тесты; существенная 🚪 code-review сразу,
      рутинная — одним сводом
    → технически готовый подблок → интеграция → следующий разрешённый подблок
    │
    ▼ (когда весь scope блока реализован и внутренние гейты пройдены)
ПРИЁМКА/LAUNCH — ручная проверка блока → readiness → согласие на версию →
  выкатка → проверка 🚪 launch-check
    │
    ▼
LEARN — retro, владелец решает: свой скоуп или RICE-скоринг бэклога
    │
    └──── новый скоуп ──→ SCOPE A/B при необходимости ──→ ДЕЛЬТА ФУНДАМЕНТА
                          ──→ ИТЕРАЦИОННАЯ DELIVERY C

  🚪 — гейт (пара producer → reviewer, независимый ревьюер + владелец отдельно)
```

Петля не обязана возвращаться в `frame`: после первого релиза путь (backbone)
обычно не пересматривается. Новый scope адресно обновляет A/B, фундамент — только
если меняются его границы, затем каждый подблок проходит C just-in-time.
Пересмотр пути целиком — по явному решению владельца, не автоматика.

**Definition C входит в итерацию delivery; по умолчанию активна одна пишущая
линия.** Можно согласовать единый delivery-пакет на несколько связанных
подблоков, перечисляющий их порядок, проверки и STOP. Тогда подробная постановка,
impact check, реализация и интеграция каждого идут подряд без нового чата или
согласия. Большой блок разрешено делить на несколько последовательных пакетов,
если единый контекст становится ненадёжным. Подблок, которого нет в пакете,
готовностью входов не получает допуск. Если владелец явно разрешил два
пакета одновременно, каждой пишущей сессии нужен свой git worktree и
назначенная область правок. Два окна одной рабочей копии не изолированы.

**Для согласованного полного delivery — схема трёх веток** (подробности — «Эпик и git» ниже):
`main` (прод, только выпущенные релизы), `stage` (общий ствол
разработки — сюда сливаются технически готовые эпики и здесь принимается
кандидат всего блока), `<task-id>` (ветка эпика, от текущей
головы `stage`). Definition C работает прямо в `stage` — там же, где
`docs/product/`; Delivery уходит в отдельный `git worktree` на ветке
эпика, только когда у эпика такая ветка есть.

При явно согласованной параллельности отдельные деревья изолируют правки (Definition C
пишет в `docs/product/`, Delivery — в `docs/delivery/`), а `status.md` —
единственный файл, где конфликт слияния ожидаем: обе сессии пишут в него
сразу после каждого события. Разрешается обычным `merge` `stage` в
ветку эпика (не наоборот, пока эпик не слит обратно) — правки лежат в
разных разделах документа, если конфликт только текстовый — агент объединяет записи в рамках пакета;
противоречащие друг другу решения/допуски возвращает владельцу, не выбирает сам. Такой `merge` тянет в ветку эпика и остальные
изменения `stage` (`docs/product/`, если Definition C успела что-то
дописать, и коммиты слияния других эпиков) — это ожидаемо, не «тихая
правка» и не «неверная база» (`code-reviewer`, «Процессные файлы в
дифе»).

## Фазы

### Frame

| Фаза | Вопрос, на который отвечает | Артефакт | Гейт |
|---|---|---|---|
| `frame` | Какую проблему, для кого и зачем решаем? | `brief` | `brief-review` |

`brief-writing` обязан закрыть фиксированный набор категорий, не на
собственное усмотрение — см. «Чек-лист брифа» ниже. Гейт запускается
всегда: независимости и полноты чек-листа это касается в первую очередь.

### Scope блока и подробная проработка подблока

`definition` разделена во времени. Этапы A/B дают тонкий, но достаточный scope
всего блока для проектирования общего фундамента. Этап C не выполняется заранее
для всех эпиков: он открывает очередную итерацию delivery и подробно описывает
только текущий подблок. Владелец согласует B и каждый C отдельно; независимый
гейт применяется к текущему C.

| Этап | Вопрос | Что делает | Артефакт |
|---|---|---|---|
| **A. Путь** | Какой у пользователя путь целиком, без деталей? | `user-story-mapping` строит backbone, владелец подтверждает поток целиком | `story_map` (backbone) |
| **B. Scope и подблоки** | Что входит в блок и что должен знать фундамент? | Путь режется на подблоки; владелец решает по каждому — scope или backlog. Фиксируются общий результат/DoD, основные потоки и правила, зависимости, out of scope, архитектурно значимые ограничения, визуальный концепт и IA. Детальные сценарии и эдж-кейсы каждого подблока здесь не обязательны | `story_map` (подблоки и scope), `backlog`, `wireframes` (концепт), `ia` |
| **C. Подробность текущего подблока** | Что именно строим в этой итерации? | После принятого фундамента и непосредственно перед реализацией: истории, сценарии, эдж-кейсы, разметка и вайрфреймы только выбранного подблока. Затем владелец согласует его целиком, проходит `story-map-review`, при необходимости `visual-design`, и запускается impact check | `story_map` (истории), `wireframes`, `visual_design` |

**A/B обязательны для scope блока; C и его `story-map-review` обязательны для
каждого реализуемого подблока.** Они не обязаны находиться в одном чате или быть
завершены по всему блоку до фундамента.
Для выбранного полного продуктового маршрута гейты не отключаются по размеру
проекта. В маршруте без delivery технический фундамент и его проверки не
применяются: C-подблоки идут последовательно как продуктовая/дизайн-работа после
своих гейтов, без impact, `epic-prep` и кода. Выбор зафиксирован в
project_profile, не решается каждым скиллом заново.

**`<task-id>` каждого эпика назначается на этапе B, не позже.** Как только
эпик вошёл в скоуп релиза (не в `backlog`) — короткий kebab-slug
(`oplata-podpiski`), сразу в строку «Скоуп релиза» `status.md`. Эпик из
`backlog`, поднятый позже отдельным заходом, получает `<task-id>` в момент,
когда его туда возвращают, тем же правилом. `epic-prep` и
`story-map-reviewer` **читают** `<task-id>`, не присваивают его — иначе
гейту `story-map-review` (он идёт уже на этапе C, до `epic-prep`) писать
отчёт некуда.

### Фундамент архитектуры и безопасности блока

Этот раздел применяется, когда в согласованный маршрут включён delivery.
Для результата «дизайн/продуктовая проработка без разработки» не требовать
архитектурную фазу до этапа C; применимость записана в паспорте проекта.

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| Фундамент/дельта (`phase: architecture`) | Как всё устроено технически в целом? | `architecture` (фундамент) | `architecture-review` |
| Адресная дельта в delivery | Что текущему подблоку нужно изменить в фундаменте? | `architecture` (дельта, только если impact check вернул `delta_required`) | `architecture-review` |

Стартует после принятия A/B: фундамент опирается на границы, основные потоки,
общие правила, зависимости и архитектурно значимые ограничения блока. Он не
ждёт подробной спецификации всех подблоков и не пытается угадать их детали.
Для существующего проекта это дельта к доверенному фундаменту, а не его
пересоздание.

`architecture-design` сверяет scope блока с текущим кодом и фундаментом.
Противоречие продуктовой логики и технических ограничений — блокер
класса Б: владелец решает, меняется ли спецификация или архитектура. После
такого решения затронутые продуктовые артефакты и `story-map-review` обновляются
адресно; это возврат по находке, а не обязательный дополнительный круг для
каждого эпика.

**Триггер фундамента — принятый тонкий scope A/B.** После B
`user-story-mapping` предлагает отдельную задачу `architecture-design` и
останавливается. Итерационная delivery не начинается, пока фундамент/дельта
блока не прошёл применимый архитектурный гейт.

После детального C текущего подблока выполняется impact check по триггерам из
WORKING_AGREEMENT §3. Без триггеров и конкретного вопроса фиксируется
`covered_by_foundation` с `assessment: local-no-trigger-check`, и субагент не
вызывается. При конкретном
вопросе или триггере `architecture-advisor` даёт read-only заключение и может
вернуть `covered_by_foundation` с `assessment: architecture-advisor`. Только `delta_required`
запускает `architecture-design` в режиме адресной дельты и `architecture-review`;
после принятия итерация продолжается с `epic-prep`.

### Delivery — по эпику

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| `epic-prep` | Как перевести принятые спецификацию и архитектуру эпика в последовательность работ? | `plan` (задачи с полной спецификацией: что делать, критерий приёмки, эдж-кейсы, НФТ, значимость) | `handoff-review` |
| `implementation` | Код, тесты, доказательства | код, `test_report` | `code-review` — **по значимости задачи**, см. ниже |
| Приёмка блока | Работает ли совокупный результат так, как задумано? | принятый кандидат блока | владелец, ручная проверка блока перед launch |

До `epic-prep` у текущего подблока есть принятый фундамент и один из двух входов:
запись `covered_by_foundation` с допустимым `assessment` либо принятая адресная
архитектурная дельта. `epic-prep` переводит подробную спецификацию и этот вход в
задачи. Если нарезка обнаруживает пропущенную развилку, она возвращает подблок в
impact check, а не принимает решение под видом плана. Отдельного
документа-перевода `task_spec` нет (см. «Реестр артефактов»): из принятых
входов сразу создаётся plan с полной спецификацией и значимостью каждой задачи.

`implementation` работает субагентом, но не на весь эпик одним вызовом —
у субагента, вызванного через `Agent`, самого доступа к `Agent` нет
(платформенное ограничение), поэтому гейт `code-review` он провести не
может: реализует задачи подряд и останавливается перед ближайшим гейтом
(сразу после коммита существенной задачи, или перед сводным проходом на
последней задаче эпика), возвращая диапазон диффа. Гейт ведёт вызывающая
сторона — `orchestrate`, а в интерактивном режиме владелец (`orchestrate`,
«Ведение пары producer → reviewer»): существенная задача — `code-review`
сразу на неё (взял задачу → закоммитил → стоп → `code-review` → если
`rework` — `implementation-repair` → повторное ревью → только по
`approved` — вызывающая сторона зовёт `implementation` заново с этим
вердиктом, тот записывает его в `test_report` и берёт следующую задачу);
рутинная — без гейта, идёт дальше сразу внутри того же вызова, все
рутинные задачи эпика разом накрывает один сводный `code-review` перед
тем, как эпик считается готовым (см. `implementation`, «Результат»). Так
один эпик — это несколько вызовов субагента, перемежающихся гейтами,
которые ведёт вызывающая сторона, а не один сквозной вызов на весь эпик.

**Эпик закрыт целиком — определяет вызывающая сторона, не сам
субагент.** `implementation` не знает, была ли задача, которую он только
что закрыл, последней в эпике — это видно по `test_report` после того,
как пройден её гейт. Не осталось ни одной незакрытой задачи и (если были
рутинные) пройден свод — вызывающая сторона сама объявляет эпик готовым,
`implementation` для этого заново не зовётся.

**Отдаёт эпик владельцу не голым «готово».** Вместе с `test_report`
(автотесты, что прошло/упало) — если эпик касается UI, ещё и скриншоты
затронутых экранов/состояний, снятые самим агентом браузерной
автоматизацией проекта, если она есть (см. `implementation`, «Если задача
трогает UI»): вызывающая сторона на этом же шаге отправляет сами файлы
владельцу, не просто путь в документе (`orchestrate`, раздел про
готовность эпика) — владелец не должен впервые увидеть экран только на
совокупной приёмке блока и не должен идти в файловую систему за
тем, что можно показать сразу.

Когда закрыты все задачи эпика и такое слияние входит в фазовый пакет — агент
сливает ветку в `stage` (`orchestrate`, «Эпик и git»), сохраняет техническое
доказательство и переходит к следующему перечисленному эпику. Скриншоты и smoke
показываются по ходу, но не создают обязательный пользовательский STOP.
Совокупная ручная приёмка выполняется на `stage` после завершения всех эпиков
крупного блока. Эпик вне согласованного фазового пакета автоматически не стартует.

**Результат ручной приёмки блока — тоже факт, который кто-то обязан записать.**
Отмечает владелец, его словами, в диалоге — не автоматика. Нашёл дефект —
никакого отдельного бага-артефакта заводить не надо, чинится тем же
`plan`, но пишет его **`epic-prep`** (третий, самый узкий режим —
«дописать задачу по дефекту», не с нуля резать эпик), не `orchestrate`:
`plan` — `committed`, у него уже есть автор с `outputs: [plan]`, `plan`
которого правит кто-то ещё — второй незаявленный писатель того же
артефакта (`ARCHITECTURE.md` §4). `orchestrate` фиксирует факт в
`status.md` и зовёт `epic-prep`, сам `plan` не трогает — то же правило,
что и для любого другого committed-документа.

**Тот же режим — не только сразу после теста своего эпика.** Триггер —
любой момент, когда владелец сообщает баг в уже реализованной
функциональности, включая холодную сессию месяцами позже, без памяти о
том, как эпик делался: `epic-prep` находит задачу-источник (по файлу —
через «Изменённые файлы эпика» в `test_report` нужного эпика, или прямо
по названному эпику) и сверяет сообщённое поведение с критерием приёмки
и сценарием, которые уже записаны (`epic-prep`, «Третий режим — задача по
дефекту» — там же обе ветки: подтвердилось расхождение или нет).
**Совпадает с зафиксированным — это не баг**, чинить нечего: правка была
бы тихой сменой продуктовой логики без решения владельца (класс Б), а не
починкой. Дописанная так задача (когда расхождение подтвердилось) — тот
же формат, что у любой (что делает, критерий приёмки, эдж-кейсы, значимость),
просто источник другой, и `handoff-review` на неё осознанно не запускается
заново (не пробел, а решение: цена гейта на одну задачу не оправдана).
Дальше — стандартный путь: `implementation` берёт её как первую
незакрытую задачу (`plan` не несёт своего состояния, см.
`implementation`), коммитит поверх «Проверено по коммит (свод)»
`test_report` — не поверх поля последней задачи «Истории», которое могло
устареть, если по своду была починка (`code-reviewer`, «Режим "Свод"») —
доводит до `code-review` (задача по дефекту — существенная всегда, тот
же приём, что у первой задачи эпика), и только после этого тест
переподтверждается. Дефект достаточно крупный, чтобы не быть задачей
внутри эпика (по факту — новая функциональность, не багфикс) — не задача
`plan`, а новый эпик через `backlog`, тем же путём, что и любой другой.
Блок не принят, пока дефект не исправлен и проверка не переподтверждена, а не
потому что «владелец в целом попробовал».

### Значимость архитектурного влияния и задачи

Independent-ревью технических гейтов (`architecture-review`,
`code-review`) — на старшей модели, с лимитом 2 — существует потому, что
владелец сам не судит архитектуру и код (`Лимит циклов` ниже). Но платить
эту цену **на каждую единицу без разбора** — отдельный архитектурный документ
для любого подблока и любую задачу — избыточно: большая часть срезов не несёт
нового технического решения. Цена гейта привязана к реальному влиянию.

**Архитектурный impact подблока** фиксируется до `epic-prep`:
- **`covered_by_foundation`** — фундамент полностью покрывает подблок. При
  отсутствии триггеров и конкретного вопроса запись имеет
  `assessment: local-no-trigger-check`; при наличии вопроса или триггера —
  `assessment: architecture-advisor` и обоснование advisor.
  Дельта и `architecture-review` не нужны в обоих случаях.
- **`delta_required`** — read-only `architecture-advisor` подтвердил влияние на
  данные/миграции, auth/права, деньги/PII, интеграцию, конкурентность/
  идемпотентность, инфраструктуру/НФТ или межподблочный контракт. Дельту пишет
  `architecture-design`, затем она проходит `architecture-review`.
- **`blocked`** — не хватает продуктового решения или принятый фундамент
  противоречит срезу; зависимая реализация остановлена.

**Задача `plan`** (`epic-prep`, нарезка на задачи) — так же, значимость с причиной:
- **Существенная** — авторизация/доступ/деньги/PII, что-то из чек-листа
  безопасности, новая/меняемая модель данных, новая внешняя интеграция,
  необратимое/массовое действие, фоновая/отложенная обработка,
  конкурентный доступ к общему состоянию, прямая реализация принятой
  архитектурной дельты, владелец сам назвал зоной риска — **и первая
  задача эпика всегда**, вне зависимости от триггеров выше: она задаёт
  каркас, который повторят остальные, и в доменах без auth/данных/интеграций
  (CLI, инструмент, библиотека) — единственная гарантированная
  индивидуальная проверка эпика, иначе весь эпик такого домена уходит в
  один свод без единого предварительного взгляда. Индивидуальный
  `code-review`, как обычно.
- **Рутинная** — всё остальное. Без индивидуального гейта: `implementation`
  коммитит и идёт дальше, самостоятельно записывая «Проверено по коммит»
  (не через вердикт ревьюера — его не было). Все рутинные задачи эпика
  разом накрывает один сводный `code-review` перед тем, как эпик считается
  готовым — свой счёт лимита (2 цикла на весь свод, не на задачу внутри
  него), рework свода чинит только конкретную задачу, где найдено 🔴, не
  всю пачку (`implementation`, «Результат»; `code-reviewer`, «Режим
  "Свод"»).

**Что не пропускается никогда:** классификация — не тихое решение
продюсера. `handoff-reviewer` сверяет impact-запись и значимость каждой задачи
на правдоподобие следующим шагом (`handoff-reviewer`, критерии 5 и 6) — это
не новый вызов, тот же гейт, что уже есть, просто с двумя дополнительными
пунктами чек-листа. Пропущенный impact-триггер не чинится правкой текста:
нужно вернуться к advisor/дельте и реально пройти нужный гейт (`handoff-reviewer`,
«Куда уходит находка»). Ошибочно рутинная задача — чинится правкой поля
в `plan`, обычный `rework`.

**Цена принимаемого риска.** Дефект в рутинной задаче ловится позже, чем
раньше (в своде, не сразу после задачи) — источник экономии, не
бесплатный трюк. Трассировка на конкретный коммит сохраняется («Проверено
по коммит» пишется всегда, вне зависимости от того, был гейт или нет), так
что находка свода всё равно указывает на конкретную задачу для починки.

### Launch и Learn

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| `launch` | Выкатили в прод, работает ли вживую? | `release_notes` | `launch-check` |
| `learn` | Что узнали и что меняем? | `learnings` | — |

`launch` — когда все эпики крупного блока реализованы и совокупный кандидат
принят владельцем на `stage`:
реальная выкатка (домен, хостинг) — решение по каждому продукту своё, но
шаг проверяемый, но выполняется только после отдельного допуска
конкретной версии и окружения. При готовности без допуска — остановка,
не merge и не публикация (WORKING_AGREEMENT, раздел 5).

После `learn` (`retro`) процесс не возвращается в `frame` автоматически —
владельца явно спрашивают, что дальше: он называет следующий скоуп сам,
либо просит прогнать `backlog` через RICE-скоринг. Выбранное — сначала в
A/B для изменения scope, затем в дельту фундамента, если затронуты его границы,
и в итерационную delivery C для каждого выбранного подблока. Путь (этап A)
пересматривается только если новый scope меняет его существенно.

## Чек-лист брифа

`brief-writing` обязан закрыть explicit, не на собственное усмотрение —
каждый пункт явным ответом или явным «не применимо, почему»:

1. Проблема, для кого, зачем (Job Story).
2. Полезное действие — что продукт делает для пользователя.
3. Бизнес-модель — на чём зарабатываем, если применимо.
4. Жёсткие ограничения — бюджет, сроки, технологии, юридическое.
5. Целевые платформы и аудитория.
6. Критерии успеха продукта.
7. Out of scope — что осознанно не делаем.
8. Риски и допущения.

`brief-review` проверяет именно полноту этого списка — не общее впечатление
о качестве текста.

## Итерационная delivery, этап C — правила детализации подблока

**Строго последовательно внутри пакета.** Следующий подблок не начинается, пока
текущий не согласован владельцем, не прошёл `story-map-review`, impact check и
оговорённую техническую интеграцию. Иной порядок или параллельность должны быть
явно разрешены и иметь независимые зависимости/области записи.

Пройденный `story-map-review` даёт вход impact check, а не автоматически
`epic-prep`. Готовность входа не запускает соседний подблок.

**Владелец видит эпик целиком, не историю за историей.** Агент предлагает
свою версию — истории со сценарием и эдж-кейсами, вайрфреймы экранов —
владелец правит, добавляет, убирает по всему эпику разом; после этого
сохраняется, переходят к следующему.

**Визуальный концепт и информационная архитектура наследуются из этапа B**,
не пересогласуются на каждом эпике — вайрфреймы эпика опираются на уже
принятое направление, не переспрашивают его заново.

**Визуальный проход (`visual-design`) не гейтован собственным ревьюером —
экономия, не дыра.** У него нет права писать в `wireframes` или
`architecture` — оба остаются за их заявленными писателями
(`user-story-mapping`/`wireframe-spec` и `architecture-design`).
Находка «тихое расширение скоупа» (новое поле, сущность, смена
навигации, которых не было в согласованных `wireframes`/`story_map`)
ловится не отдельным гейтом, а тем же блокером класса Б, что и любая
другая продуктовая развилка («Блокеры и эскалация»): `visual-design`
только флагует находку, а `user-story-mapping` (он же вызывает
`visual-design` этим же шагом — `visual-design/SKILL.md`, «Правила
поведения») вносит её в `wireframes` тем же проходом, пишет блокер
класса Б строкой в «Открытые вопросы» `status.md` и **перезапускает
`story-map-review` на этот эпик заново** — новый цикл со своим лимитом
1, отметка «утверждено» снимается тем же проходом. Находка трогает
архитектуру, не только UI-слой — блокер эскалируется в
`architecture-design` тем же путём, что «Конфликт эпика с техническим
фундаментом» выше («Архитектура и безопасность блока»); `visual-design`
`architecture` не правит никогда.

**Единица среза без критерия приёмки и сценария — сигнал, что этап C не
завершён для этого эпика**, а не то, что можно добрать позже в подготовке
к разработке (`epic-prep`): подготовка эпика — переводчик технической
формы, не автор продуктовой.

## Реестр артефактов

Идентификатор — то, чем оперируют `inputs`/`outputs` скиллов. Путь может
меняться, идентификатор — нет.

**Кто артефакт производит и кто потребляет, здесь не записано.** Это объявляют
сами скиллы своим frontmatter (`phase` + `outputs` — производитель,
`inputs`/`optional_inputs` — потребители), и вторая запись того же факта
разъезжается с первой молча. Нужен граф — он выводится из frontmatter
установленных скиллов: `grep`'ом по каталогу плагинов рядом с тем, что
читает этот документ (`${CLAUDE_PLUGIN_ROOT}` смотрит на свой плагин —
каталог всех плагинов на уровень выше него), не по пути `plugins/` — этого
каталога в репозитории продукта нет, только в репозитории процессов.

Реестр отвечает ровно на один вопрос: **какому идентификатору какой путь**.

### Управляющие — для любого проекта

| ID | Путь | Класс |
| --- | --- | --- |
| `project_profile` | `docs/process/PROJECT_PROFILE.md` | committed |
| `roadmap` | `docs/process/ROADMAP.md` | committed |
| `work_package` | `docs/process/packages/<package-id>.md` | committed |
| `approvals` | `docs/process/APPROVALS.md` | committed |

Их ведёт orchestrate или текущий ответственный агент при прямом вызове метода.
Шаблоны лежат в [templates/](templates/), внутри process-core, доступны и
после установки плагина. Пакет может охватывать анализ или дизайн, а не только
эпик; его ID и ссылка на допуск находятся в status. Для существующего проекта
сначала согласовать соответствие прежних документов этим ID, не плодить
вторые версии. bootstrap и автоматическая миграция — не часть P1.

**Roadmap и backlog отвечают на разные вопросы.** Roadmap хранит выбранные
этапы, зависимости, внутренний план и DoD. Backlog — невыбранные идеи и эпики,
их зависимости, если известны. Порядок работ меняется по решению владельца;
при выборе идеи агент обновляет roadmap, ссылается на исходную запись backlog
и отдельно предлагает ближайший пакет. Подробности реализации — в plan,
а status отражает факт выполнения. Наличие идеи или этапа не даёт допуска.

**`task_spec` как отдельный артефакт убран.** Раньше между продуктовой
проработкой и нарезкой задач стоял документ-перевод; при детальности,
которую теперь даёт Definition, этап C (сценарии, эдж-кейсы уже описаны
явно), отдельный слой перевода дублировал то, что уже написано. Полная
спецификация каждой задачи — прямо в `plan`.

**Прототипы `visual_design` — `committed`, не `scratch`.** Это не
одноразовый черновик ревью, а источник точного переноса в реализацию:
самодостаточные HTML/CSS-файлы, открываются прямо в браузере, без сборки.
`docs/product/VISUAL_DESIGN.md` — растущий документ (по образцу
`wireframes`): один раздел «Токены» (палитра, типографика, форма базовых
элементов, один раз на продукт) плюс по разделу на каждый зафиксированный
эпик со ссылками на файлы прототипов этого эпика.

### Delivery (в разрезе эпика)

| ID | Путь | Класс |
|---|---|---|
| `architecture` | `docs/delivery/ARCHITECTURE.md` (фундамент) + `docs/delivery/<task-id>/ARCHITECTURE.md` (только реальная дельта текущего подблока) | committed |
| `architecture_impact` | `.process/<task-id>/architecture_impact.md` (`covered_by_foundation`, `delta_required` или `blocked`) | scratch |
| `plan` | `docs/delivery/<task-id>/PLAN.md` | committed |
| `test_report` | `docs/delivery/<task-id>/TEST_REPORT.md` | committed |
| `release_notes` | `docs/delivery/RELEASE.md` | committed |

**`<task-id>` — это эпик, не релиз.** Короткий kebab-slug, уникальный в
пределах продукта: `oplata-podpiski`, `import-csv`. Эпики одного релиза
идут последовательно (см. «Итерационная delivery, этап C») — каждый получает свой
`<task-id>` и свой каталог `docs/delivery/<task-id>/`, но технический
фундамент (`docs/delivery/ARCHITECTURE.md`) один на продукт, вне каталогов
эпиков, и читается/расширяется каждым.

**`release_notes` — один на релиз, не на эпик.** Пишется на шаге `launch`,
после того как все эпики скоупа реализованы и протестированы — не после
каждого отдельного эпика.

**Откуда взять `<task-id>` текущего эпика — не из этого реестра.** Здесь
только путь по идентификатору, а какой именно `<task-id>` сейчас активен —
состояние, а не путь: строка «Текущий эпик» в шапке `.process/status.md`.
Несколько каталогов в `docs/delivery/` — не выбирай по дате изменения
файлов. Строки нет — спроси владельца, не гадай.

**Карты пути пользователя своего ID не имеют** — по тому же правилу
триггера, что и реестр ADR. Инструмент диагностический, но триггер — не
разовая просьба владельца: `information-architecture` сам предлагает её
по умолчанию на этапе B (см. таблицу выше), и ложится она разделом внутрь
`ia`, не отдельным файлом. Заводить артефактом первого класса заранее —
та же преждевременная каталогизация, от которой отказались с ADR;
своего ID нет именно поэтому, а не потому, что диагностика редкая.

**Отдельного реестра ADR нет.** Архитектурные решения и причины, по
которым они приняты, живут разделом «Решения» внутри `architecture` —
фундамента или адресной дельты, где решение реально принято. Реестр
`docs/delivery/adr/` заводится **по триггеру**: как только понадобилось
сослаться на решение из другого эпика.

кодовые тесты и вердикты ревью.

## Эпик и git

Три ветки, не одна: `main` (прод — только то, что реально выпущено),
`stage` (общий ствол разработки — детальный C, слияние готовых эпиков,
совокупная приёмка блока), `<task-id>` (ветка эпика,
от `stage`, живёт до слияния обратно).

Эта схема применяется только если выбрана в project_profile. Сначала агент
проверяет существующие ветки, remotes, незакоммиченные изменения и CI/CD.
После согласования настройки сам создаёт нужные ветки и PR; не перекладывает
Git-команды на владельца. Нельзя создавать stage или включать публикацию
лишь потому, что вызван orchestrate. Для проекта без репозитория Git может
быть неприменим — это отражается в паспорте.

**«Ветка» и «База» — два разных поля в шапке `plan`.** «Ветка» — всегда
`<task-id>`, отдельная ветка эпика: слияние выполняет агент в рамках
согласованного допуска (см. ниже), отдельная ветка ничего не стоит даже для мелкого
эпика, а вариант «работать прямо в `stage`» создавал больше проблем
(не поддержан ни одним читателем ниже по цепочке), чем экономил. «База»
— всегда конкретный коммит, не имя ветки: имя уедет вперёд между записью
и чтением.

**`epic-prep` работает в `stage`, не в будущей ветке эпика.** Читает принятый
фундамент и impact-запись (либо принятую дельту), пишет `plan` и фиксирует его в `stage` — двумя
коммитами (`epic-prep`, «Результат»): первый — сам `plan`, второй — база
и записи `status.md`, потому что коммит не может ссылаться на собственный
хэш. Ветка эпика создаётся от **второго** коммита (в нём уже всё), диф
задач считается от **первого** (он и есть «База» в `plan`). Дальше
агент сам создаёт ветку от второго коммита, если это входит в пакет. Если
согласована отдельная пишущая сессия, создаёт worktree; новую пользовательскую
задачу — только по прямой просьбе. Строка «Эпики в работе параллельно» в status
появляется только при разрешённой параллельности, а не при любой новой сессии.
При закрытии пакета убрать завершённую запись, сохранив историю допуска.

**Каждый следующий эпик ветвится от проверенной базы по принятой Git-схеме.**
Если он перечислен в согласованном development-пакете, после технического
закрытия предыдущего агент продолжает без пользовательского STOP. Эпик вне
пакета ждёт новой контрольной точки и команды владельца.
При разрешённой параллельности отсутствие ещё не влитой зависимости —
вопрос к владельцу, не повод выдумывать сигнатуры или незаметно менять базу.

**Слияние ветки эпика в `stage` — часть закрытия эпика технически, не
факультатив, и у неё есть исполнитель.** Если слияние в тестовую ветку входит в согласованный пакет и эпик прошёл
`code-review` по всем задачам — `orchestrate` сливает его ветку в
`stage` сам, тем же проходом, где отмечает эпик закрытым технически.
`stage` — место накопления кандидата блока; владелец принимает совокупный
результат на фазе приёмки, а не обязан тестировать каждый внутренний эпик.
Дефект, найденный на приёмке, — задача в `plan` соответствующего эпика, как обычно (см. «Delivery — по
эпику»); ветка эпика не удаляется до подтверждения теста, чинится на
ней же и переливается заново.

**Релиз — отдельный допуск неизменяемой версии.** Launch-check сначала
проверяет readiness, включая сводное ревью. Затем предъявляет точный commit,
digest/конфигурацию/миграции и окружение, получает согласие владельца в approvals.
Только после сверки версии выполняет разрешённые merge/deploy и проверку
после выкладки. Если main запускает прод автоматически, merge уже является
выпуском и требует допуска до действия. Merge-коммит, отличный от одобренного,
должен быть подготовлен и проверен заранее либо выкладка использует одобренный
immutable-артефакт (WORKING_AGREEMENT, раздел 5). Само слияние не доказывает,
что сервис запущен; readiness не означает согласия на прод.

`handoff-review` читает предъявленную редакцию `plan` до её фиксации;
поле базы пока может быть плейсхолдером. После гейта `epic-prep` фиксирует
эту редакцию и базу; смысловые изменения требуют пересмотра вердикта.
`code-review` проверяет коммитный диф, не незакоммиченное рабочее дерево
(существенная задача — сразу и отдельно; рутинная —
сводом в конце эпика, «Значимость архитектурного влияния и задачи») — своя цепочка
баз вне зависимости от значимости: первая задача эпика — от базы `plan`;
каждая следующая — от коммита, записанного в поле «Проверено по коммит»
у предыдущей закрытой задачи (`implementation`, «Результат»; для
рутинной задачи это поле пишет сам `implementation`, не вердикт
ревьюера) — не заново от базы `plan`, иначе каждая проверка заново
ревьюила бы уже закрытые задачи.

## Гейты

| Гейт | Где | Ревьюер | Что проверяет прежде всего |
|---|---|---|---|
| `brief-review` | конец `frame` | `brief-reviewer` | Закрыт ли чек-лист брифа целиком; реалистичны ли ограничения; не решение ли записано вместо проблемы |
| `story-map-review` | конец каждого эпика в Definition, этап C | `story-map-reviewer` | Целостность и охват именно этого эпика; сценарии и эдж-кейсы не поверхностны; тихое расширение скоупа |
| `architecture-review` | конец фундамента; конец адресной дельты, только после `delta_required` | `architecture-reviewer` | Соответствие scope/фундаменту; преждевременная сложность; совместимость; безопасность |
| `handoff-review` | конец `epic-prep` | `handoff-reviewer` | Задачи полностью специфицированы; impact-триггеры не пропущены; фундамент/дельта достаточны; значимость задач правдоподобна |
| `code-review` | конец **каждой существенной** задачи отдельно; все **рутинные** задачи эпика разом — один сводный проход перед концом эпика («Значимость архитектурного влияния и задачи») | `code-reviewer` | Соответствие этой задаче; доказательства, а не моки; регресс; безопасность (rate limiting, доступ к чужим данным, инъекции) |
| `launch-check` | перед выпуском релиза | — (самопроверка внутри скилла) | Доказательства и откат; отдельный допуск точной версии; выкладка и проверка фактической версии |

**Эта таблица — единственный источник связки гейт → ревьюер.** Продюсер,
объявляющий гейт в своём `Результат`, называет имя гейта из своего же
`gate:` во frontmatter и отсылает сюда — не хранит имя ревьюера у себя.

**Независимый ревьюер и согласование владельца — две разные проверки, не
взаимозаменяемые.** Владелец видит эпик целиком и решает, нужен ли он
вообще такой, какой есть, — у него есть контекст и сочувствие к
собственным решениям. Независимый ревьюер (чистый контекст, без истории
обсуждения) ловит ровно то, что владелец на своём месте не увидит:
внутренние противоречия, пропущенные сценарии, тихое расширение. Ни один
не заменяет другого — оба гейта стоят, даже когда владелец уже согласовал.

**`launch-check` — единственный гейт без пары producer → reviewer.** Он сам
себе и продюсер, и проверка: предмет — честный факт («живая проверка и
выкатка правда состоялись»), доступа к которому у второго агента ровно
столько же, сколько у первого.

## Пара producer → reviewer

Как проходится гейт.

```
продюсер (скилл, основной контекст, или субагент)
    ↓ артефакт
ревьюер (субагент, чистый контекст, другая модель)
    ↓ вердикт
починка по замечаниям  ──→  повторное ревью
```

**Особенность `code-review`: продюсер — субагент, но пару ведёт не он.**
`implementation` (`ARCHITECTURE.md` §1) — субагент по той же причине, что
и всегда: код, диффы и вывод тестов не должны оседать в сессии владельца.
Но вызванный через `Agent` субагент сам доступа к `Agent` не имеет —
пару «продюсер → ревьюер → починка → повторное ревью» он вести не может
физически, не по решению методологии. Ведёт её вызывающая сторона
(`orchestrate`, «Ведение пары producer → reviewer») — как и для любого
другого гейта, только продюсер здесь не скилл в основном контексте, а
субагент, который после каждой существенной задачи останавливается и
возвращает диапазон диффа, а не сдаёт готовый артефакт целиком.
Повторяется это **на каждую существенную задачу эпика отдельно**
(«Значимость архитектурного влияния и задачи»), не один раз на весь эпик. Рутинные
задачи в этот цикл не заходят по одной — накапливаются и уходят одним
сводным вызовом `code-reviewer` перед концом эпика. Владельцу наружу
выходит не каждый шаг цикла и не каждая отдельная задача, а итог по
эпику целиком (готово или блокер) — это по-прежнему держит вызывающая
сторона, не показывая владельцу внутренние гейты один за другим.

**Ревьюеру не пересказывают историю решений.** Ему дают пути к артефакту и
список документов для самостоятельного чтения.

### Кто чинит

| Что чинится | Кто |
|---|---|
| Всё по умолчанию | Сам продюсер, по списку замечаний |
| `architecture` (фундамент или адресная дельта) | Отдельный repair-скилл (`architecture-repair`, основной контекст) |
| код (`test_report`) | Отдельный repair-субагент (`implementation-repair`, вызывает его тот, кто ведёт гейт — `orchestrate` или владелец, не `implementation`: у него самого нет доступа к `Agent`) |

### Лимит циклов

**Лимит зависит от гейта, не один на всех** — граница проходит по
экспертизе владельца, не по формальному присутствию в сессии: где
владелец сам может судить о качестве (он уже вёл интервью или лично
согласовал результат), независимый круг один; где не может («я не
силён» — его собственные слова про архитектуру) — независимая проверка
единственная защита, там кругов два.

| Гейт | Лимит | Почему |
|---|---|---|
| `brief-review` | 1 | Владелец сам вёл интервью — уже был реальной проверкой |
| `story-map-review` (на эпик) | 1 | Владелец уже согласовал эпик целиком лично, до этого гейта |
| `handoff-review` | 1 | Плохой `plan` дёшево ловится ниже — всплывёт как нестыковка на первой же задаче `code-review` |
| `architecture-review` (фундамент; и каждая реальная дельта отдельно) | 2 | Владелец не судит архитектуру сам — независимый круг здесь единственная защита |
| `code-review` (на каждую существенную задачу отдельно; свод рутинных — 2 на всю пачку) | 2 | Та же причина — разработку владелец не оценивает сам |

Циклом считается ревью, дошедшее до вердикта по существу. Остановка
`code-reviewer` до чтения кода (незакоммиченная работа) цикл не расходует
— это `blocked` с просьбой закоммитить, не вердикт по существу.

**Для гейтов delivery-трека единица — задача, свод рутинных задач, или
конкретный эпик, не продукт целиком.** У `code-review` свой счёт на
каждую существенную задачу, независимый от соседних задач того же
эпика: задача 1.2 исчерпала лимит — это не трогает счётчик задачи 1.3.
Сводный `code-review` по рутинным задачам — тоже своя единица, свой
счёт: 2 цикла на весь свод целиком, не на задачу внутри него
(«Значимость архитектурного влияния и задачи»). У `architecture-review` — свой
счёт на фундамент и отдельно на каждую реальную дельту.

**Лимит 1 — как это работает.** Ревью прошло, только некритичные находки
— как обычно, идём дальше, находки в артефакт как принятый долг. Есть
критичные/важные — продюсер чинит по списку замечаний, и этого достаточно
по умолчанию: второй независимый круг не запускается автоматически,
отдельной пометки об этом заводить не надо — обычный ход, не исключение.
**Ревьюер сам решает, покрывает ли это его находку.** Замечание —
обычное («не хватает эдж-кейса», «нечёткий критерий») — чинится и на этом
всё. Замечание непредвиденное или реально блокирующее (например,
подозрение, что чинить пришлось бы не текст, а продуктовое решение) —
вердикт `blocked`, тот же формат остановки, что у любого блокера
(«Блокеры и эскалация»), не второй круг ревью. Владелец хочет
перепроверить именно эту правку независимо — вызывает того же ревьюера
сам, явным запросом.

**Лимит 2 — как раньше.** После второго:

| Что осталось | Действие |
|---|---|
| Критичные замечания | Стоп, эскалация владельцу |
| Только некритичные | Идём дальше; замечание пишется в артефакт как принятый долг |

## Правила движения

**Перед применением любого пункта — границы WORKING_AGREEMENT.** Выполнять
только согласованный пакет; допуск не выводится из наличия файлов или
approved-ревью. Прямой вызов скилла не обходит это правило. Уже согласованные
ревью и предусмотренные исправления не требуют повторного вопроса перед
каждым вызовом; следующий этап и прод требуют своего допуска.

**Количество проверок определяет бюджет доказательств договора, а не число
строк в сценарии.** Обязательные гейты ниже сохраняются, но дополнительные
тесты и ревью должны закрывать названный риск или отдельный слой отказа.
Сценарии разрешено группировать; полный regression повторяется после изменения
его входов, а не как ритуал после каждого внутреннего шага.

1. **Гейт не пропускается.** Все гейты из таблицы «Гейты» запускаются
   всегда, когда применимы, — глубины, отключающей гейты, в этой версии
   процесса нет. Применимость — не то же самое, что «отключено»:
   `architecture-review` при `covered_by_foundation` и `code-review` на
   рутинную задачу по конструкции не запускаются («Значимость архитектурного
   влияния и задачи»), но impact и классификация проверяются
   `handoff-reviewer` — не молчаливый пропуск. Механизма, который бы это
   форсировал технически, нет — запуск скиллов ручной; оркестратор
   проверяет наличие ревью и говорит, если его нет.
2. **Продюсер сам называет свой гейт при сдаче артефакта.** Раздел
   «Результат» скилла-продюсера называет `gate:` из своего frontmatter и
   предлагает запустить ревьюера (имя — из таблицы «Гейты»). Владелец
   тут же соглашается — продюсер сам организует ревью, запустив именно
   ревьюера этого гейта, не `general-purpose`; сам считает лимит циклов
   своего гейта (1 или 2 — «Лимит циклов» выше, зависит от гейта); получив
   вердикт, сам записывает его в `status.md`. **Исключение — `code-review`
   в режиме субагента**: продюсер (`implementation`) физически не может
   этого сделать сам, гейт вместо него ведёт вызывающая сторона («Пара
   producer → reviewer», «Особенность `code-review`»).
3. **Возврат назад — нормальный ход.** После `learn` — обновление A/B, если
   меняется scope, затем дельта фундамента по влиянию и C текущего подблока,
   не автоматический возврат в `frame`.
4. **Один активный пакет по умолчанию.** Один delivery-пакет может содержать
   несколько последовательных подблоков; это не разрешение параллельности.
   Владелец может
   явно разрешить несколько пакетов или прохождение нескольких контрольных
   точек без остановки; точные границы записываются в approvals. По окончании
   этого разрешения — стоп, даже если следующий шаг очевиден.

5. **Продуктовые артефакты обновляются, а не форкаются.** Если `learn`
   изменил понимание, правится `brief`, а не заводится `BRIEF_v2.md`.
6. **Правка committed-артефакта задним числом, когда на нём уже что-то
   построено, помечает то, что построено поверх старой версии.** Строка в
   «Открытые вопросы» `status.md`. Условие — именно «уже что-то
   построено», не факт повторной записи: плановая перезапись документа
   без потребителя ниже по цепочке строку не пишет. Снимается тем
   продюсером, который следующим переписывает названный артефакт.

## Блокеры и эскалация

**Владелец подтверждает поток до гейта.** Стоп-точки вроде «backbone —
ждёт подтверждения владельцем» (этап A), «скоуп/концепт — ждёт
подтверждения» (этап B) или «эпик N — ждёт подтверждения» (этап C) —
не формальность и не то, что можно пропустить, если выглядит очевидным:
это открытый вопрос в `status.md`, и он блокер сам по себе, до всякого
гейта. Гейт (`story-map-review` и т.д.) проверяет качество уже
подтверждённого — не подменяет само подтверждение и не запускается вместо
него.

### Класс А — машинно-разрешимые

Окружение, отсутствующее evidence, устаревшие артефакты. Агент чинит сам,
**одна попытка**, дальше — эскалация. Чинить разрешено только окружение,
перезапуск проверки и собственные черновики; продуктовый код, продуктовую
документацию и смысл задачи — нельзя.

### Класс Б — решения владельца (всегда стоп)

- Продуктовые развилки: scope, приоритет, отказ от функции.
- **Конфликт эпика с техническим фундаментом** (эпик требует то, что
  фундамент не поддерживает, или наоборот) — явный пример этого класса,
  не отдельная категория: решает владелец, меняется продуктовая логика
  эпика или пересматривается фундамент.
- Архитектурные развилки.
- Fallback-политика, обратная совместимость, миграции, source of truth,
  семантика раскатки.
- Юридические и этические вопросы.
- Деньги и любые внешние обязательства.

```

Фаза:     {фаза}
Источник: {скилл или субагент}
```

## Состояние пайплайна

`.process/status.md` — рабочий индекс: где мы сейчас и что дальше.
Обновляется **немедленно** после каждого события.

### Файла ещё нет — заводит любой, кому обязательно писать

`orchestrate` — не условие для существования `status.md`: писать в него
обязаны все продюсеры committed-артефактов. Первый, кому это точно
понадобится, — продюсер, который заводит первый `<task-id>` (эпик).
Не нашёл файла — заводит его сам: строки `.gitignore`, шапка с путём к
реестру и версией `process-core`, молча, тем же проходом, что и основную
разрешённую работу. До записи проверяет существующие инструкции и решения.
Если интервью/состав модулей ещё не согласованы, ставит «не определено» и
выясняет недостающее по WORKING_AGREEMENT; не запускает все фазы по умолчанию.

**Зачем строка версии.** Артефакта нет по пути из реестра — это не всегда
значит «файл пропал»: продукт мог быть собран под более раннюю раскладку
`process-core`, где реестр называл другой путь для того же идентификатора.
Строка «Версия process-core» в шапке даёт сравнить, прежде чем говорить
владельцу «файла нет», — расхождение версий и пропавший артефакт требуют
разных действий (обновить продукт под текущую раскладку vs восстановить
работу).

**Состав модулей и допуск — в управляющих документах.** Status ссылается
на project_profile, roadmap, текущий work_package и запись approvals,
а не хранит копию триажа. Старое поле «Масштаб процесса» сохраняется как
история до согласованного перехода; не переводить проект молча на новую схему.

Перед возобновлением сверить версию входов/результата с записью проверки
и допуска. Автоматического валидатора в P1 нет: проверка ручная, по commit
или редакции. Несовпадение требует анализа и решения, а не переноса отметки
«утверждено» на новый результат.

### `status.md` коммитится — он не производная целиком

«Фаза есть» — производная, пересканировать `docs/` достаточно. «Утверждено»
— не производная тем же способом: это факт о пройденном гейте, а
доказательство (отчёт ревьюера) — законно одноразовый `scratch`. Отметку
«утверждено» не понижают без позитивной улики (артефакт правился после
неё, или владелец сам сказал, что гейт не проходили).

```markdown
# Статус

> Реестр артефактов: <абсолютный путь к этому PROCESS.md>
> Версия process-core: <значение version из plugin.json>
> Паспорт и roadmap: <ссылки>
> Крупный блок / часть / подблок: <ID блока и scope | фундамент | итерационная delivery + task-id | приёмка/релиз>
> Активный пакет / редакция: <ID и ссылка>
> Узел roadmap / родитель: <ID и ссылки; постановка/планирование/исполнение>
> Рабочее место: <фактическая папка/worktree, репозиторий, ветка/HEAD, незакоммиченные изменения, окружение; проверить при продолжении>
> Допуск: <ID записи approvals или «нет»>
> Следующая контрольная точка: <результат и условие остановки>
> Передача: <результат/доказательства/версии; открытое; следующий рекомендуемый узел и модель>
> Источник плана продолжения: <roadmap путь/редакция; связанный plan/раздел или «нет»>
> Текущий эпик: <task-id или «нет»>
> Скоуп релиза: <список "task-id (EPIC-XXX)" эпиков этого релиза, с отметкой закрыт/нет>
> Эпики в работе параллельно: <task-id> → <путь worktree>, ... — или строки нет, если параллельной работы нет
```

На фазовой границе или при реальной передаче держать в status компактный раздел
«Следующий чат»: блок «Что дальше» только по указанному roadmap/plan и готовый
промт с рабочим местом, блоком/фазой, источниками, результатом, целью/DoD,
проверками и STOP. Между внутренними шагами той же фазы достаточно записи
прогресса без полного промта; `state.phase` при этом остаётся `ready`. Если
следующего узла в плане нет, записать задачу
планирования или приёмки, не создавать реализационный шаг из памяти. Это
handoff, не новый допуск.

Чек-листы ниже нужны только для выбранного продуктового маршрута. Для
исследования достаточно статуса его пакета, вопросов и ссылок на результат.
Пройденные проверки и согласия — ссылки на записи approvals с точной версией.

```markdown
## Фазы — продукт
- [x] Frame — утверждено
- [x] Definition, этап A (путь) — утверждено
- [x] Definition, этап B (тонкий scope и подблоки) — утверждено
- [ ] Фундамент архитектуры/безопасности блока — в процессе (review 1 из 2)

## Итерационная delivery — по подблокам scope
### `<task-id-1>`
- [x] Проработка (истории, сценарии, эдж-кейсы, вайрфреймы) — утверждено
- [x] story-map-review — утверждено
- [x] visual-design — утверждено (или «пропущено владельцем», с причиной)
- [x] architecture impact — covered_by_foundation (триггеры проверены)
- [x] epic-prep — утверждено
- [ ] implementation — задача 1.3 на code-review (цикл 1 из 2)
- [ ] Технически закрыт и слит в stage — нет

### `<task-id-2>`
- [ ] Проработка C — не начато (ждёт закрытия `<task-id-1>` или иной порядок пакета)

## Приёмка крупного блока
- [ ] Совокупный кандидат на stage — не готов
- [ ] Ручная приёмка владельца — не начата
- [ ] Launch readiness / отдельный prod-допуск — не начато

## Открытые вопросы к владельцу
- …

## Заблокировано внешне
- …
```

**Каждый `<task-id>` хранит единую итерацию от C до интеграции.** Подблоки не
взаимозаменяемы и по умолчанию идут последовательно: следующий ждёт технического
закрытия предыдущего, но не отдельного ручного теста и нового чата, если оба
перечислены в delivery-пакете. Явно разрешённый иной порядок записывается в
пакете и зависимостях (см. «Правила движения» п.4).

### Проверка перед докладом владельцу

Прежде чем сказать «готово»: файлы артефактов существуют? отмеченные
выполненными шаги имеют результат? блокеры отражены? Расхождение —
сначала чинить `status.md`, потом докладывать.
