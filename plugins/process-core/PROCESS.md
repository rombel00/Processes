# Процесс: фазы, артефакты, гейты

Карта жизненного цикла продукта — от идеи до выученного урока: фазы, что каждая
даёт, где стоят проверки, как классифицируются блокеры и как ведётся состояние.

Это **рабочий документ**: его читает скилл `orchestrate` и любой, кто ведёт
продукт по процессу. Правила разработки самих скиллов — отдельно, в
`ARCHITECTURE.md` репозитория процессов.

> Все пути в этом документе — пути **в репозитории продукта**, над которым идёт
> работа, а не в репозитории процессов.

> **Версия 2.** Процесс всегда идёт полным путём — глубины «бриф и сразу код» /
> «только хребет» больше нет, ни один гейт не выключается по масштабу продукта.
> Единица работы delivery — эпик, не релиз целиком. История решения и то, что
> было раньше, — в `GAPS.md` репозитория процессов.

## Карта

```
FRAME
  frame ── 🚪 brief-review
    │
    ▼
DEFINITION
  A. путь ──── владелец подтверждает поток целиком
    │
    ▼
  B. путь → эпики, владелец режет скоуп релиза, каждому — свой task-id,
     визуальный концепт + информационная архитектура — на весь продукт
    │
    ├──────────────────────────────┐
    ▼                               ▼
  C. эпик 1 🚪 ──┐            ТЕХНИЧЕСКИЙ ФУНДАМЕНТ
     эпик 2 🚪 ──┤            (стартует сразу по скоупу,
     эпик 3 🚪 ──┤            параллельно с C; конфликт
     (строго последовательно  эпика с фундаментом — блокер
     между собой; каждый —    класса Б)
     истории + сценарии +           │
     эдж-кейсы + вайрфреймы)        │
    │                               │
    └──── эпик прошёл C ────────────┘
              (не дожидаясь остальных эпиков C)
                    ▼
DELIVERY — по эпику скоупа, начинается для эпика сразу по его C, может
  идти в отдельной сессии параллельно с Definition C следующих эпиков —
  делать один за другим внутри самой Delivery всё равно надо
  подготовка эпика 🚪 (тех.надстройка + сверка с фундаментом + задачи)
    │
    ▼
  разработка эпика (субагент, задача за задачей) 🚪 code-review
    │
    ▼
  владелец: ручной тест ЭТОГО эпика, или команда «дальше» → следующий эпик
    │
    ▼ (когда все эпики скоупа реализованы и протестированы)
LAUNCH — выкатка в прод 🚪 launch-check
    │
    ▼
LEARN — retro, владелец решает: свой скоуп или RICE-скоринг бэклога
    │
    └──── новый скоуп ──→ ТЕХНИЧЕСКИЙ ФУНДАМЕНТ (сверка) ──→ DEFINITION C

  🚪 — гейт (пара producer → reviewer, независимый ревьюер + владелец отдельно)
```

Петля замыкается в `ТЕХНИЧЕСКИЙ ФУНДАМЕНТ` → `DEFINITION C`, не в `frame`:
после первого релиза путь (backbone) обычно не пересматривается — только
берётся новый скоуп эпиков. Пересмотр пути целиком — по явному решению
владельца, не автоматика.

**Definition C и Delivery — две независимые последовательности, не одна
цепочка.** Каждая идёт строго последовательно **сама по себе** (следующий
эпик Definition C не начат, пока не согласован предыдущий; следующий эпик
Delivery не начат, пока не закрыт предыдущий), но друг друга не ждут:
Delivery эпика стартует, как только именно этот эпик прошёл
`story-map-review`, — не когда прошли все эпики скоупа. Практически это
означает две сессии одновременно: одна продолжает Definition C следующих
эпиков, другая ведёт Delivery уже готового — они не конфликтуют по
файлам (Definition C пишет в `docs/product/`, Delivery — в
`docs/delivery/`), а общее состояние (`status.md`) синхронизируется
обычным коммитом, как любая параллельная работа в git.

## Фазы

### Frame

| Фаза | Вопрос, на который отвечает | Артефакт | Гейт |
|---|---|---|---|
| `frame` | Какую проблему, для кого и зачем решаем? | `brief` | `brief-review` |

`brief-writing` обязан закрыть фиксированный набор категорий, не на
собственное усмотрение — см. «Чек-лист брифа» ниже. Гейт запускается
всегда: независимости и полноты чек-листа это касается в первую очередь.

### Definition — три этапа одной фазы

`definition` не заканчивается одним артефактом за один проход — она состоит
из трёх этапов, всегда именно в этом порядке, с двумя видами владельческого
согласования (по этапу B и по каждому эпику C) плюс независимым гейтом на
каждый эпик этапа C.

| Этап | Вопрос | Что делает | Артефакт |
|---|---|---|---|
| **A. Путь** | Какой у пользователя путь целиком, без деталей? | `user-story-mapping` строит backbone, владелец подтверждает поток целиком, прежде чем что-либо детализируется | `story_map` (backbone) |
| **B. Эпики и скоуп** | Что входит в этот релиз? | Путь режется на эпики; владелец решает по каждому — в релиз или в бэклог. Тут же — визуальный концепт (стиль, цвета, платформы — обсуждением, не рисунком) и информационная архитектура (структура разделов/навигации), обе на весь продукт целиком | `story_map` (эпики), `backlog`, `wireframes` (концепт), `ia` |
| **C. Проработка по эпику** | Что именно строим внутри эпика? | Строго последовательно, эпик за эпиком: истории с детальным сценарием, эдж-кейсами, разметкой + вайрфреймы экранов этого эпика. Владельцу — эпик целиком на согласование (не история за историей). Гейт `story-map-review` — на этот эпик, сразу после согласования владельцем, не в конце всех эпиков | `story_map` (истории), `wireframes` (экраны эпика) |

**Все три этапа обязательны, гейт (`story-map-review` этапа C) — всегда.**
Опциональности по глубине больше нет.

**`<task-id>` каждого эпика назначается на этапе B, не позже.** Как только
эпик вошёл в скоуп релиза (не в `backlog`) — короткий kebab-slug
(`oplata-podpiski`), сразу в строку «Скоуп релиза» `status.md`. Эпик из
`backlog`, поднятый позже отдельным заходом, получает `<task-id>` в момент,
когда его туда возвращают, тем же правилом. `epic-prep` и
`story-map-reviewer` **читают** `<task-id>`, не присваивают его — иначе
гейту `story-map-review` (он идёт уже на этапе C, до `epic-prep`) писать
отчёт некуда.

### Технический фундамент

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| `foundation` | Как всё устроено технически в целом? | `architecture` (фундамент) | `architecture-review` |

Стартует сразу по итогам этапа B (список эпиков и скоуп известны — деталей
сценариев ждать не нужно) и идёт **параллельно** с этапом C. Если по ходу
проработки эпика (этап C) всплывает техническая деталь, которую фундамент
не покрывает, — это блокер класса Б (см. «Блокеры и эскалация»): фундамент
пересматривается прежде, чем эпик считается закрытым, а не копится молча.

**Триггер — сам конец этапа B, не отдельное решение владельца.**
`user-story-mapping` предлагает запустить `architecture-design` (режим
«Фундамент») сразу, как только скоуп зафиксирован — не дожидаясь, что это
позже заметит `orchestrate`.

Пишет и то, и другое один и тот же скилл, `architecture-design`, с одним
`phase: architecture` во frontmatter на оба режима — фундамент и
надстройку эпика. Различает их не `phase`, а то, кто и когда его вызвал:
сам по себе на этапе B — фундамент; `epic-prep` на конкретном эпике —
надстройка.

### Delivery — по эпику

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| `epic-prep`, шаг 1 | Что фундамент не покрывает для этого эпика? | `architecture` (надстройка) | `architecture-review` |
| `epic-prep`, шаг 2 | Что именно делает разработчик, задача за задачей? | `plan` (задачи с полной спецификацией: что делать, критерий приёмки, эдж-кейсы, НФТ) | `handoff-review` |
| `implementation` | Код, тесты, доказательства | код, `test_report` | `code-review` |
| (без имени) | Работает ли это так, как задумано? | — | владелец, ручная проверка эпика |

`epic-prep` — один скилл, два внутренних шага, не отдельный
документ-перевод между ними (то, что раньше называлось `task_spec`, ушло
вместе с этим слиянием, см. «Реестр артефактов»): сначала техническая
надстройка поверх фундамента для этого эпика, с обязательной сверкой на
противоречия (конфликт — блокер класса Б, не решается тихо кем-то одним
по умолчанию), потом — только после её `architecture-review` — нарезка на
задачи с полной спецификацией каждой.

`implementation` работает субагентом на весь эпик за один вызов, но
`code-review` — гейт на **каждую задачу отдельно**, не на эпик разом:
взял задачу → закоммитил → `code-review` → если `rework` —
`implementation-repair` → повторное ревью → только по `approved` (или
исчерпанному лимиту с одними некритичными находками) — следующая задача
(см. `implementation`, «Результат»). Один вызов субагента покрывает весь
эпик по числу задач, но не одну общую проверку в конце.

**Отдаёт эпик владельцу не голым «готово».** Вместе с `test_report`
(автотесты, что прошло/упало) — если эпик касается UI, ещё и скриншоты
затронутых экранов/состояний, снятые самим агентом браузерной
автоматизацией проекта, если она есть (см. `implementation`, «Если задача
трогает UI»). Владелец не должен первым увидеть экран только в момент
собственного ручного теста.

Когда закрыты все задачи эпика — владельцу на ручной тест этого эпика,
или, по явной команде владельца, сразу следующий эпик без остановки (тогда
несколько эпиков тестируются вместе позже).

**Результат ручного теста — тоже факт, который кто-то обязан записать.**
Отмечает владелец, его словами, в диалоге — не автоматика. Нашёл дефект —
не правь мимо процесса: это отдельная задача в `plan` того же эпика (или
новый эпик, если по объёму больше мелочи), она идёт тем же путём —
`implementation` → `code-review` — и только после этого тест
переподтверждается. Эпик не закрыт, пока не встал плюс, а не потому что
«владелец в целом попробовал».

### Launch и Learn

| Фаза | Вопрос | Артефакт | Гейт |
|---|---|---|---|
| `launch` | Выкатили в прод, работает ли вживую? | `release_notes` | `launch-check` |
| `learn` | Что узнали и что меняем? | `learnings` | — |

`launch` — когда все эпики скоупа реализованы и протестированы владельцем:
реальная выкатка (домен, хостинг) — решение по каждому продукту своё, но
шаг обязательный и проверяемый, не рекомендация.

После `learn` (`retro`) процесс не возвращается в `frame` автоматически —
владельца явно спрашивают, что дальше: он называет следующий скоуп сам,
либо просит прогнать `backlog` через RICE-скоринг. Выбранное — сначала к
техническому фундаменту (сверка/расширение), потом в Definition C для
новых эпиков, с той же двусторонней консультацией с фундаментом по ходу,
что и в первом релизе. Путь (этап A) пересматривается только если новый
скоуп меняет его существенно — не по умолчанию.

## Чек-лист брифа

`brief-writing` обязан закрыть explicit, не на собственное усмотрение —
каждый пункт явным ответом или явным «не применимо, почему»:

1. Проблема, для кого, зачем (Job Story).
2. Полезное действие — что продукт делает для пользователя.
3. Бизнес-модель — на чём зарабатываем, если применимо.
4. Жёсткие ограничения — бюджет, сроки, технологии, юридическое.
5. Целевые платформы и аудитория.
6. Критерии успеха продукта.
7. Out of scope — что осознанно не делаем.
8. Риски и допущения.

`brief-review` проверяет именно полноту этого списка — не общее впечатление
о качестве текста.

## Definition, этап C — правила детализации по эпику

**Строго последовательно — внутри самой Definition C.** Следующий эпик не
начинается, пока текущий не согласован владельцем целиком и не прошёл
`story-map-review`. Продуктовая логика должна укладываться слой за слоем,
параллельная проработка двух эпиков не допускается.

**Это не то же самое, что ожидание Delivery.** Эпик, прошедший
`story-map-review`, может тут же уйти в `epic-prep`/Delivery — обычно в
другой сессии — пока эта сессия продолжает Definition C следующего эпика.
Definition C ждёт только сама себя, не готовность Delivery предыдущих
эпиков (`PROCESS.md`, «Карта»).

**Владелец видит эпик целиком, не историю за историей.** Агент предлагает
свою версию — истории со сценарием и эдж-кейсами, вайрфреймы экранов —
владелец правит, добавляет, убирает по всему эпику разом; после этого
сохраняется, переходят к следующему.

**Визуальный концепт и информационная архитектура наследуются из этапа B**,
не пересогласуются на каждом эпике — вайрфреймы эпика опираются на уже
принятое направление, не переспрашивают его заново.

**Единица среза без критерия приёмки и сценария — сигнал, что этап C не
завершён для этого эпика**, а не то, что можно добрать позже в подготовке
к разработке (`epic-prep`): подготовка эпика — переводчик технической
формы, не автор продуктовой.

## Реестр артефактов

Идентификатор — то, чем оперируют `inputs`/`outputs` скиллов. Путь может
меняться, идентификатор — нет.

**Кто артефакт производит и кто потребляет, здесь не записано.** Это объявляют
сами скиллы своим frontmatter (`phase` + `outputs` — производитель,
`inputs`/`optional_inputs` — потребители), и вторая запись того же факта
разъезжается с первой молча. Нужен граф — он выводится из frontmatter
установленных скиллов: `grep`'ом по каталогу плагинов рядом с тем, что
читает этот документ (`${CLAUDE_PLUGIN_ROOT}` смотрит на свой плагин —
каталог всех плагинов на уровень выше него), не по пути `plugins/` — этого
каталога в репозитории продукта нет, только в репозитории процессов.

Реестр отвечает ровно на один вопрос: **какому идентификатору какой путь**.

### Продуктовые

| ID | Путь | Класс |
|---|---|---|
| `brief` | `docs/product/BRIEF.md` | committed |
| `market` | `docs/product/MARKET.md` | committed |
| `personas` | `docs/product/PERSONAS.md` | committed |
| `interview_report` | `docs/product/INTERVIEWS.md` | committed |
| `lean_canvas` | `docs/product/LEAN_CANVAS.md` | committed |
| `story_map` | `docs/product/STORY_MAP.md` | committed |
| `backlog` | `docs/product/BACKLOG.md` | committed |
| `wireframes` | `docs/product/WIREFRAMES.md` | committed |
| `ia` | `docs/product/IA.md` | committed |
| `learnings` | `docs/product/LEARNINGS.md` | committed |

**`backlog` заменяет `roadmap`.** Плоский список эпиков вне текущего
скоупа, без порядка и без тем/гипотез — только сам эпик и, если известно,
поле «Зависит от» (что должно случиться раньше, чтобы этот эпик стал
возможен). Порядок появляется только когда владелец явно называет
следующий скоуп или запрашивает RICE-скоринг (см. «Launch и Learn» выше) —
не хранится заранее.

**`task_spec` как отдельный артефакт убран.** Раньше между продуктовой
проработкой и нарезкой задач стоял документ-перевод; при детальности,
которую теперь даёт Definition, этап C (сценарии, эдж-кейсы уже описаны
явно), отдельный слой перевода дублировал то, что уже написано. Полная
спецификация каждой задачи — прямо в `plan`.

### Delivery (в разрезе эпика)

| ID | Путь | Класс |
|---|---|---|
| `architecture` | `docs/delivery/ARCHITECTURE.md` (фундамент) + `docs/delivery/<task-id>/ARCHITECTURE.md` (надстройка эпика) | committed |
| `plan` | `docs/delivery/<task-id>/PLAN.md` | committed |
| `test_report` | `docs/delivery/<task-id>/TEST_REPORT.md` | committed |
| `release_notes` | `docs/delivery/RELEASE.md` | committed |

**`<task-id>` — это эпик, не релиз.** Короткий kebab-slug, уникальный в
пределах продукта: `oplata-podpiski`, `import-csv`. Эпики одного релиза
идут последовательно (см. «Definition, этап C») — каждый получает свой
`<task-id>` и свой каталог `docs/delivery/<task-id>/`, но технический
фундамент (`docs/delivery/ARCHITECTURE.md`) один на продукт, вне каталогов
эпиков, и читается/расширяется каждым.

**`release_notes` — один на релиз, не на эпик.** Пишется на шаге `launch`,
после того как все эпики скоупа реализованы и протестированы — не после
каждого отдельного эпика.

**Откуда взять `<task-id>` текущего эпика — не из этого реестра.** Здесь
только путь по идентификатору, а какой именно `<task-id>` сейчас активен —
состояние, а не путь: строка «Текущий эпик» в шапке `.process/status.md`.
Несколько каталогов в `docs/delivery/` — не выбирай по дате изменения
файлов. Строки нет — спроси владельца, не гадай.

**Карты пути пользователя своего ID не имеют** — по тому же правилу
триггера, что и реестр ADR. Скилл есть, инструмент диагностический:
применяется, когда на конкретном продукте понадобилось найти точки
трения, и ложится разделом внутрь `ia`. Заводить его артефактом первого
класса заранее — та же преждевременная каталогизация, от которой
отказались с ADR.

**Отдельного реестра ADR нет.** Архитектурные решения и причины, по
которым они приняты, живут разделом «Решения» внутри `architecture` —
фундамента или надстройки эпика, где решение реально принято. Реестр
`docs/delivery/adr/` заводится **по триггеру**: как только понадобилось
сослаться на решение из другого эпика.

### `.process/` — состояние и черновики

| ID | Путь | Класс | Git |
|---|---|---|---|
| `status` | `.process/status.md` | **committed** | коммитится — единственный файл `.process/` в git |
| `<artifact>_draft` | `.process/<artifact>_draft.md` | scratch | игнорируется |
| `<artifact>_review` | `.process/<artifact>_review.md` | scratch | игнорируется — гейт без эпика: `brief-review` (продуктовый трек) или `architecture-review` **технического фундамента** — эпика на этот момент ещё нет ни в одном из двух случаев |
| `<artifact>_review` | `.process/<task-id>/<artifact>_review.md` | scratch | игнорируется — гейт delivery-трека, `story-map-review` эпика или `architecture-review` **надстройки** конкретного эпика, внутри `<task-id>` |

`test_report` — `committed` (см. таблицу «Delivery» выше), несмотря на то,
что раньше жил как черновик рядом с отчётами ревью: часть его содержимого
невоспроизводима (живая проверка в реальном окружении).

## Эпик и git

Как `epic-prep` и `implementation` определяют базу для дифа, и что из
этого проверяет `launch-check`.

**«Ветка» и «База» — два разных поля в шапке `plan`.** «База» — всегда
конкретный коммит, не имя ветки: имя уедет вперёд между записью и чтением.
«Ветка» — `<task-id>` (отдельная ветка эпика) или «основная» (работа идёт
прямо в ней, без отдельной ветки).

**Первый эпик релиза** — «База» — голова основной ветки на момент начала
эпика. **Каждый следующий эпик релиза** — «База» — коммит, в который
влилась ветка предыдущего закрытого эпика, не голова основной «на всякий
случай»: если предыдущий эпик ещё не влит, следующий технически не может
на него опираться.

**Слияние ветки эпика в основную — часть закрытия эпика, не факультатив.**
Момент — по продукту (сразу после ручного теста владельца, или пачкой
перед `launch`), но один и тот же для всех эпиков одного релиза, не
решается заново на каждом. `launch-check` проверяет, что все ветки эпиков
релиза реально слиты, — отдельно от проверки, что домен и хостинг
настроены (это про прод, не про git).

Гейты (`code-review`, `handoff-review`) считают диф от базы, записанной в
шапке `plan`, а не рабочее дерево — незакоммиченная работа для ревьюера не
существует.

## Гейты

| Гейт | Где | Ревьюер | Что проверяет прежде всего |
|---|---|---|---|
| `brief-review` | конец `frame` | `brief-reviewer` | Закрыт ли чек-лист брифа целиком; реалистичны ли ограничения; не решение ли записано вместо проблемы |
| `story-map-review` | конец каждого эпика в Definition, этап C | `story-map-reviewer` | Целостность и охват именно этого эпика; сценарии и эдж-кейсы не поверхностны; тихое расширение скоупа |
| `architecture-review` | конец «Технического фундамента» и конец технической надстройки каждого эпика | `architecture-reviewer` | Соответствие эпику/фундаменту; преждевременная сложность; совместимость; безопасность |
| `handoff-review` | конец `epic-prep` | `handoff-reviewer` | Задачи полностью специфицированы (критерии, эдж-кейсы, НФТ); надстройка не противоречит фундаменту |
| `code-review` | конец **каждой** задачи эпика, не эпика целиком | `code-reviewer` | Соответствие этой задаче; доказательства, а не моки; регресс; безопасность (rate limiting, доступ к чужим данным, инъекции) |
| `launch-check` | перед выпуском релиза | — (самопроверка внутри скилла) | Живая проверка обещанного; готовность отката; реальная выкатка сделана |

**Эта таблица — единственный источник связки гейт → ревьюер.** Продюсер,
объявляющий гейт в своём `Результат`, называет имя гейта из своего же
`gate:` во frontmatter и отсылает сюда — не хранит имя ревьюера у себя.

**Независимый ревьюер и согласование владельца — две разные проверки, не
взаимозаменяемые.** Владелец видит эпик целиком и решает, нужен ли он
вообще такой, какой есть, — у него есть контекст и сочувствие к
собственным решениям. Независимый ревьюер (чистый контекст, без истории
обсуждения) ловит ровно то, что владелец на своём месте не увидит:
внутренние противоречия, пропущенные сценарии, тихое расширение. Ни один
не заменяет другого — оба гейта стоят, даже когда владелец уже согласовал.

**`launch-check` — единственный гейт без пары producer → reviewer.** Он сам
себе и продюсер, и проверка: предмет — честный факт («живая проверка и
выкатка правда состоялись»), доступа к которому у второго агента ровно
столько же, сколько у первого.

## Пара producer → reviewer

Как проходится гейт.

```
продюсер (скилл, основной контекст, или субагент)
    ↓ артефакт
ревьюер (субагент, чистый контекст, другая модель)
    ↓ вердикт
починка по замечаниям  ──→  повторное ревью
```

**Исключение — `code-review`.** Продюсер (`implementation`) — тоже
субагент, не скилл в основном контексте (`ARCHITECTURE.md` §1): код,
диффы и вывод тестов не должны оседать в сессии владельца. Пара «продюсер
→ ревьюер → починка → повторное ревью» здесь целиком внутри контура
`implementation`-субагента — но повторяется **на каждую задачу эпика
отдельно**, не один раз на весь эпик: он сам вызывает `code-reviewer`
после каждой задачи и, если нужно, `implementation-repair`, прежде чем
взять следующую. Наружу выходит только итог по эпику целиком (готово или
блокер), не каждый шаг цикла и не каждая отдельная задача.

**Ревьюеру не пересказывают историю решений.** Ему дают пути к артефакту и
список документов для самостоятельного чтения.

### Кто чинит

| Что чинится | Кто |
|---|---|
| Всё по умолчанию | Сам продюсер, по списку замечаний |
| `architecture` (фундамент или надстройка) | Отдельный repair-скилл (`architecture-repair`, основной контекст) |
| код (`test_report`) | Отдельный repair-субагент (`implementation-repair`, вызывает его сам `implementation`) |

### Лимит циклов

**Лимит зависит от гейта, не один на всех** — граница проходит по
экспертизе владельца, не по формальному присутствию в сессии: где
владелец сам может судить о качестве (он уже вёл интервью или лично
согласовал результат), независимый круг один; где не может («я не
силён» — его собственные слова про архитектуру) — независимая проверка
единственная защита, там кругов два.

| Гейт | Лимит | Почему |
|---|---|---|
| `brief-review` | 1 | Владелец сам вёл интервью — уже был реальной проверкой |
| `story-map-review` (на эпик) | 1 | Владелец уже согласовал эпик целиком лично, до этого гейта |
| `handoff-review` | 1 | Плохой `plan` дёшево ловится ниже — всплывёт как нестыковка на первой же задаче `code-review` |
| `architecture-review` (фундамент; и каждая надстройка эпика отдельно) | 2 | Владелец не судит архитектуру сам — независимый круг здесь единственная защита |
| `code-review` (на каждую задачу отдельно) | 2 | Та же причина — разработку владелец не оценивает сам |

Циклом считается ревью, дошедшее до вердикта по существу. Остановка
`code-reviewer` до чтения кода (незакоммиченная работа) цикл не расходует
— это `blocked` с просьбой закоммитить, не вердикт по существу.

**Для гейтов delivery-трека единица — задача или конкретный эпик, не
продукт целиком.** У `code-review` свой счёт на каждую задачу, независимый
от соседних задач того же эпика: задача 1.2 исчерпала лимит — это не
трогает счётчик задачи 1.3. У `architecture-review` — свой счёт на
фундамент и отдельно на надстройку каждого эпика.

**Лимит 1 — как это работает.** Ревью прошло, только некритичные находки
— как обычно, идём дальше, находки в артефакт как принятый долг. Есть
критичные/важные — продюсер чинит по замечаниям, но второе независимое
ревью не запускается автоматически: результат идёт владельцу как есть, с
честной пометкой «починено по замечаниям, повторно независимо не
проверено». Владелец хочет второй независимый проход — вызывает того же
ревьюера сам, явным запросом.

**Лимит 2 — как раньше.** После второго:

| Что осталось | Действие |
|---|---|
| Критичные замечания | Стоп, эскалация владельцу |
| Только некритичные | Идём дальше; замечание пишется в артефакт как принятый долг |

## Правила движения

1. **Гейт не пропускается.** Все гейты из таблицы «Гейты» запускаются
   всегда — глубины, отключающей гейты, в этой версии процесса нет.
   Механизма, который бы это форсировал технически, нет — запуск скиллов
   ручной; оркестратор проверяет наличие ревью и говорит, если его нет.
2. **Продюсер сам называет свой гейт при сдаче артефакта.** Раздел
   «Результат» скилла-продюсера называет `gate:` из своего frontmatter и
   предлагает запустить ревьюера (имя — из таблицы «Гейты»). Владелец
   тут же соглашается — продюсер сам организует ревью, запустив именно
   ревьюера этого гейта, не `general-purpose`; сам считает лимит циклов
   своего гейта (1 или 2 — «Лимит циклов» выше, зависит от гейта); получив
   вердикт, сам записывает его в `status.md`.
3. **Возврат назад — нормальный ход.** После `learn` — новый скоуп через
   технический фундамент и Definition C, не через `frame`.
4. **Один эпик одновременно — внутри каждой из двух последовательностей,
   не одна на весь процесс.** Следующий эпик Definition C не начинается,
   пока текущий не согласован; следующий эпик delivery не начинается, пока
   текущий не закрыт (кроме явной команды владельца продолжать без
   остановки на тест). Обе последовательности друг друга не ждут — эпик,
   прошедший Definition C, может быть в delivery, пока другой эпик ещё
   проходит Definition C, обычно в отдельной сессии (`PROCESS.md`,
   «Карта»).
5. **Продуктовые артефакты обновляются, а не форкаются.** Если `learn`
   изменил понимание, правится `brief`, а не заводится `BRIEF_v2.md`.
6. **Правка committed-артефакта задним числом, когда на нём уже что-то
   построено, помечает то, что построено поверх старой версии.** Строка в
   «Открытые вопросы» `status.md`. Условие — именно «уже что-то
   построено», не факт повторной записи: плановая перезапись документа
   без потребителя ниже по цепочке строку не пишет. Снимается тем
   продюсером, который следующим переписывает названный артефакт.

## Блокеры и эскалация

### Класс А — машинно-разрешимые

Окружение, отсутствующее evidence, устаревшие артефакты. Агент чинит сам,
**одна попытка**, дальше — эскалация. Чинить разрешено только окружение,
перезапуск проверки и собственные черновики; продуктовый код, продуктовую
документацию и смысл задачи — нельзя.

### Класс Б — решения владельца (всегда стоп)

- Продуктовые развилки: scope, приоритет, отказ от функции.
- **Конфликт эпика с техническим фундаментом** (эпик требует то, что
  фундамент не поддерживает, или наоборот) — явный пример этого класса,
  не отдельная категория: решает владелец, меняется продуктовая логика
  эпика или пересматривается фундамент.
- Архитектурные развилки.
- Fallback-политика, обратная совместимость, миграции, source of truth,
  семантика раскатки.
- Юридические и этические вопросы.
- Деньги и любые внешние обязательства.

### Формат остановки

```
⚠️ ПРОЦЕСС ОСТАНОВЛЕН

Фаза:     {фаза}
Источник: {скилл или субагент}

Вопросы:
1. …

Контекст: {2–3 предложения — чего не хватает и почему без ответа нельзя дальше}
```

## Состояние пайплайна

`.process/status.md` — рабочий индекс: где мы сейчас и что дальше.
Обновляется **немедленно** после каждого события.

### Файла ещё нет — заводит любой, кому обязательно писать

`orchestrate` — не условие для существования `status.md`: писать в него
обязаны все продюсеры committed-артефактов. Первый, кому это точно
понадобится, — продюсер, который заводит первый `<task-id>` (эпик).
Не нашёл файла — заводит его сам: строки `.gitignore`, шапка с путём к
реестру и версией `process-core`, молча, тем же проходом, что и основную
работу.

### `status.md` коммитится — он не производная целиком

«Фаза есть» — производная, пересканировать `docs/` достаточно. «Утверждено»
— не производная тем же способом: это факт о пройденном гейте, а
доказательство (отчёт ревьюера) — законно одноразовый `scratch`. Отметку
«утверждено» не понижают без позитивной улики (артефакт правился после
неё, или владелец сам сказал, что гейт не проходили).

```markdown
# Статус

> Реестр артефактов: <абсолютный путь к этому PROCESS.md>
> Версия process-core: <значение version из plugin.json>
> Текущий эпик: <task-id или «нет»>
> Скоуп релиза: <список task-id эпиков этого релиза, с отметкой закрыт/нет>

## Фазы — продукт
- [x] Frame — утверждено
- [x] Definition, этап A (путь) — утверждено
- [x] Definition, этап B (эпики и скоуп) — утверждено
- [ ] Технический фундамент — в процессе (review 1 из 2)

## Definition, этап C — по эпикам скоупа (своя последовательность)
### `<task-id-1>`
- [x] Проработка (истории, сценарии, эдж-кейсы, вайрфреймы) — утверждено
- [x] story-map-review — утверждено

### `<task-id-2>`
- [ ] Проработка — не начато (ждёт согласования `<task-id-1>`)

## Delivery — по эпикам скоупа (своя последовательность; эпик входит
## сюда сразу по своему story-map-review, не дожидаясь остальных C)
### `<task-id-1>`
- [x] epic-prep — утверждено
- [ ] implementation — в процессе
- [ ] Ручной тест владельца — не начато

### `<task-id-2>`
- [ ] epic-prep — не начато (ждёт закрытия `<task-id-1>` в Delivery)

## Открытые вопросы к владельцу
- …

## Заблокировано внешне
- …
```

**Definition C и Delivery — два отдельных списка блоков по `<task-id>`, не
один.** Внутри каждого списка эпики не взаимозаменяемы (закрытие одного не
значит закрытие следующего) и идут строго последовательно **внутри своего
списка**: следующий эпик Definition C ждёт согласования предыдущего в
Definition C; следующий эпик Delivery ждёт закрытия предыдущего в
Delivery. Это два разных факта — эпик может быть давно согласован в
Definition C и всё ещё ждать своей очереди в Delivery, это нормально, не
рассинхрон (см. «Правила движения» п.4).

### Checkpoint перед докладом владельцу

Прежде чем сказать «готово»: файлы артефактов существуют? отмеченные
выполненными шаги имеют результат? блокеры отражены? Расхождение —
сначала чинить `status.md`, потом докладывать.
