# CTO Review — независимое архитектурное/код-ревью

Ты (агент, вызвавший этот скилл) **не ревьюишь сам**. Твоя задача — организовать
независимую проверку и без искажений донести её результат владельцу продукта.

## Почему не ревьюишь сам

Если решение принимал ты же, в этом же диалоге — у тебя уже есть контекст
переговоров и причины выбора, и ты будешь скорее защищать свою логику, чем
проверять её. Настоящая независимость требует двух вещей одновременно:

1. **Отдельный агент без памяти этого диалога** — видит только артефакт и
   продуктовые документы, не видит, почему решения принимались именно так.
2. **По возможности — другая модель**, не только чистый контекст. Модель,
   которая писала решение, может воспроизвести те же слепые зоны даже без
   памяти диалога — потому что склонности зашиты в веса, не только в контекст.

Оба условия обязательны — без первого ревьюер просто перескажет твою же
аргументацию, без второго есть шанс, что он придёт к тем же выводам просто
в силу общей склонности модели.

## Когда запускать

По запросу владельца продукта, на границе завершения этапа или перед
финализацией PR — когда документ/код претендует на статус "готово", а не
"черновик". Не гонять на каждый мелкий шаг: это дороже (другая модель) и
медленнее обычной итерации.

## Шаги

1. **Определить объект ревью.** Если владелец не назвал явно — определи сам:
   файлы, изменённые в текущей ветке относительно `main`
   (`git diff main...HEAD --stat`), либо конкретный путь/PR, который назвал
   владелец.
2. **Не пересказывай ревьюеру историю переговоров.** Собери только: путь(и)
   к объекту ревью и список документов для самостоятельного чтения (см.
   бриф ниже). Не резюмируй "почему мы так решили" в промпте — это и есть
   утечка предвзятости, которую весь смысл скилла — избежать.
3. **Запусти независимого субагента** через инструмент `Agent`:
   - `subagent_type`: `general-purpose`
   - `model`: `opus` — сознательно другая модель, не только чистый контекст
   - `run_in_background: false` — результат нужен сразу в этом же разговоре
   - `prompt`: самодостаточный (агент не видит этот диалог) — используй
     шаблон "Бриф для ревьюера" ниже, подставив артефакт и пути к документам.
4. **Передай результат владельцу как есть**, целиком, до любых своих
   комментариев. Если хочешь добавить реакцию — отдельным, явно помеченным
   абзацем ("мой комментарий:"), не смешивая со списком находок ревьюера.
5. **Не применяй правки сам.** Ревью — вход для решения владельца, а не
   команда на исполнение. Находки ревью — это архитектурные развилки в
   терминах `CLAUDE.md`: подтверждаются владельцем, даже если ревьюер прав.

## Бриф для ревьюера (шаблон промпта для `Agent`)

```
Ты — независимый CTO-консультант. Ревьюишь [АРТЕФАКТ: путь(и)] для раннего
продукта (pre-MVP, один разработчик — AI-агент, один пользователь-владелец
на старте, стадия личной валидации). Ты не участвовал в его создании и не
знаешь, почему решения принимались именно так — оценивай только то, что
видишь в файлах.

Контекст продукта — прочитай сам, до того как оценивать:
- CLAUDE.md — правила работы, кто владелец, как принимаются решения
- docs/PRODUCT_BRIEF.md — проблема, критерии приёмки, ограничения, out of scope
- docs/LEAN_CANVAS.md — бизнес-модель, самое рискованное допущение
- docs/MARKET_RESEARCH.md — рынок, конкуренты, риски категории
- docs/ROADMAP.md — этапы, текущий статус
- docs/PROCESS.md — как принимаются решения, git-процесс

Объект ревью: [ПУТЬ(И) К АРТЕФАКТУ]

Проверь:
1. Соответствие ограничениям из брифа (бюджет, объём, out of scope) — нет ли
   решений, которые тихо расширяют scope или бюджет без явного обсуждения.
2. Внутренние противоречия — между документами, между документом и кодом,
   между разделами одного документа.
3. Преждевременная сложность — решения "на вырост", не нужные при текущем
   масштабе (один пользователь, стадия личной валидации).
4. Забытые или недооценённые риски — то, что уже названо риском в
   LEAN_CANVAS.md/MARKET_RESEARCH.md, но текущее решение это не учитывает.
5. Что сделано хорошо — независимое ревью не значит "искать только плохое";
   отметь, что решение реально закрывает и почему это разумный выбор.

Формат ответа:

1. В самом начале — общая оценка проработанности артефакта по шкале 0-5
   (0 — почти ничего не продумано, 5 — готово к реализации без открытых
   вопросов), одно предложение обоснования, почему не выше/не ниже.
2. Дальше — список находок, каждая с: чёткой формулировкой проблемы,
   конкретным сценарием, где она проявится ("если... то..."), и меткой
   важности: 🔴 критично (мешает следующему шагу) / 🟡 стоит обсудить с
   владельцем / 🟢 не блокирует, идея на будущее.

Не предлагай фичи вне брифа, не оценивай то, что не входит в объект
ревью. Ответ — на русском.
```

## Границы (чего этот скилл не делает)

- Не заменяет проверку фичи вживую в Telegram (Definition of Done,
  `docs/PROCESS.md`) — для документов и решений до кода это единственная
  доступная проверка на этой стадии, для реализованных фич она дополняет,
  а не заменяет живое тестирование.
- Не решает архитектурные развилки сам — только подсвечивает их для
  владельца.
- Не запускается автоматически на каждый коммит — ни экономически (модель
  Opus дороже), ни по темпу мелких итераций это не оправдано.
