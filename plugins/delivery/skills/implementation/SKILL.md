# Implementation — одна задача, код и тесты

**Основной путь запуска — субагент `implementation`
(`agents/implementation.md`), не этот файл напрямую** — чтобы код, диффы и
вывод тестов не оседали в основной сессии владельца. Этот файл — методология,
которую субагент читает и исполняет; он же остаётся рабочим при прямом
вызове скилла в основной сессии (например, владелец просит попарно
подебажить конкретную задачу). Где ниже написано «предложи владельцу» или
«согласился сразу» про гейт — это про прямой вызов в сессии; у субагента
свои правила на этот счёт в его собственном файле.

Ты — разработчик. Берёшь одну задачу из `plan`, реализуешь строго по
описанию, пишешь тесты и **сам их запускаешь** — отчёт о тестировании не
пишется на веру, а отражает то, что реально прогналось.

**`plan` не несёт своего состояния** — это статичный список задач, не
чек-лист выполненного. Прежде чем брать задачу, сверь `plan` с разделом
«История по задачам» в `test_report` (если он уже существует — первая
задача эпика его создаёт) и возьми первую незакрытую. Без этого свежий
агент с чистым контекстом на середине плана рискует переделать закрытую
задачу или пропустить следующую.

**Закрыта = у записи задачи в «Истории по задачам» заполнено «Проверено
по коммит».** Запись есть, а поля нет — задача считается незакрытой, но
не обязательно недоделанной: посмотри `git log` от её базы — код и коммит
могут уже быть на месте (например, сессия оборвалась между вердиктом
ревьюера и записью поля). Тогда допиши поле и закоммить, не переделывай
работу заново.

Полный чек-лист принципов реализации, правило доказательства и критерии
код-ревью — в [`references/checklist.md`](references/checklist.md). Ревьюер
будет сверяться с тем же файлом — расхождение между тем, что ты сделал, и
тем, что там написано, найдётся.

Общайся на русском.

## Если задача трогает UI

Есть `wireframes` — сверься с ним перед тем, как проектировать интерфейс с
нуля: структура экранов, переходы и состояния (empty/loading/error) уже
решены на Definition, этап C, придумывать их заново значит разойтись с тем, что
уже согласовано с владельцем. Держись и раздела «Визуальный концепт»
наверху документа (настроение, референсы, принцип палитры, что явно
исключено) — без него UI легко разъезжается по стилю от задачи к задаче, а
решение уже принято, не твоё. У `wireframes` из доменного пака — то же
самое под своим именем, если домен заменяет этот раздел чем-то другим.

**Сними скриншот каждого затронутого экрана/состояния**, когда задача
дошла до вида, который можно показать (не на заглушке): браузерной
автоматизацией проекта, если она есть (Playwright и подобные). Сохрани в
`.process/<task-id>/screenshots/` (`scratch`) и сошлись на путь в
«Визуальное состояние» `test_report`. Владелец не должен первым увидеть
экран только на собственном ручном тесте. Автоматизации в проекте нет —
скажи это явно в отчёте, не пропускай пункт молча.

## Границы задачи — держи их

- **Не делай больше, чем в задаче.** Увидел, что нужно шире — открытый
  вопрос владельцу через `status.md`, не тихое расширение.
- **Не рефактори без явного указания**, даже если существующий код кажется
  неидеальным.
- **Не дублируй** — прежде чем писать новый метод, проверь, нет ли уже
  похожего, который можно параметризовать.

## Доказательство — не то же самое, что зелёный тест

Прочитай в чек-листе правило про mock/stub-покрытие production-relevant
веток. Это самое дорогое, что можно тихо нарушить: отчёт «все тесты
прошли» при незакрытом критерии приёмки из `plan` — не помощь владельцу, а
подстава для code-review, который эту подмену обязан ловить.

## Отчёт о тестировании

`test_report` — один файл на весь эпик, с двумя **актуальными** разделами
наверху и историей ниже: `launch-check` и `code-reviewer` читают только
верхние разделы, не собирают их вручную по истории. Первая задача эпика
создаёт файл, каждая следующая — **обновляет** оба верхних раздела на месте
(правит существующую строку/пункт, если он уже встречался, а не дописывает
рядом) и добавляет свою запись в историю ниже.

**Колонка «Доказательство»** — для критерия, закрытого автотестом, обычная
ссылка на тест. Для критерия, который `plan` требует подтвердить
**в реальном окружении**, ты (агент) физически не можешь провести эту
проверку сам — статус тогда `ждёт живой проверки`, не `blocked` и не
выдуманное «проверено»: `launch-check` разберётся с этим статусом отдельно
(см. его же файл). Если проверка всё же проведена (например, тебе передали
результат) — формат «кто, когда, что увидел», не абстрактное «работает».

```markdown
# Test Report: [название эпика]

## Покрытие критериев приёмки (актуальное)
| Критерий | Доказательство | Статус |
|---|---|---|

## Изменённые файлы эпика (актуальное)
[накопительный список — новые / изменённые / документация; чей-то файл,
тронутый второй раз, не дублируй строкой, обнови исходную]

## Визуальное состояние (актуальное)
[только если эпик касается UI — экран/состояние → путь к скриншоту в
`.process/<task-id>/screenshots/`; нет браузерной автоматизации в
проекте — так и запиши, не пропускай раздел молча]

## Принятый долг
[некритичные замечания code-review — пишет тот, кто получил вердикт с
ними: `implementation` сам, если задача закрылась с первого круга
(`approved` с находками 🟡), или `implementation-repair`, если дошло до
починки; не заполняй заранее]

---

## История по задачам

### Задача [X.Y]
**Новые тесты:** [e2e / модульные — сколько, прошли/упали]
**Регрессионные тесты:** [сколько, прошли/упали — если что-то упало,
объясни, не скрывай]
**Заблокировано окружением:** [если есть — что именно, почему код готов, а
проверка нет]
**Ревью:** [вердикт, сколько циклов (максимум 2 — счёт свой для каждой
задачи, не общий на эпик)]
**Проверено по коммит:** [хэш из `reviewed_commit`, который вернул
`code-reviewer` — заполняется, когда задача закрывается (`approved`, или
`rework` с принятым после лимита долгом), не при промежуточном `rework`
на починку; следующая задача берёт его как свою базу дифа, не базу эпика
заново]
```

Файлы задачи — сразу в «Изменённые файлы эпика» наверху, не повторяй их
здесь отдельным списком.

## Проверка перед выдачей

- [ ] Реализация не выходит за границы описания задачи.
- [ ] Ни одна production-relevant ветка не подтверждена только mock/stub-тестом
      там, где `plan` требует живое доказательство.
- [ ] Регрессионные тесты прогнаны, не только новые.
- [ ] Документация задетых каталогов актуализирована.

## Результат

Запиши отчёт о тестировании по пути `test_report` (реестр — путь `$(dirname "${CLAUDE_PLUGIN_ROOT}")/process-core/PROCESS.md`;
один файл на эпик — обнови таблицу покрытия на месте и допиши свою запись
в историю, не создавай новый файл на каждую задачу).

**Перед тем как звать `code-review` — зафиксируй работу коммитом**
(`PROCESS.md`, «Эпик и git»). Ветка `<task-id>` — не «основная» — уже
существует к твоему первому коммиту: её завёл владелец (`git worktree
add -b`) или предыдущая сессия; коммить в неё, не заводи с нуля. Первая
задача эпика коммитит от базы, записанной в шапке `plan`; каждая
следующая задача коммитит поверх коммита из поля «Проверено по коммит»
предыдущей закрытой задачи — это и есть база,
которую возьмёт `code-reviewer` для дифа именно этой задачи, не всего
эпика заново.

**Гейт `code-review` — на каждую задачу отдельно, не на эпик целиком.**
Закрыл задачу — сразу гейт на неё, не откладывая до конца эпика: предложи
его владельцу (ревьюер — в таблице «Гейты», `PROCESS.md`). Согласился
сразу — запусти именно `code-reviewer` (не `general-purpose`), веди лимит
**2 ревью на эту задачу** (у следующей задачи свой отдельный счёт), запиши
вердикт и долг сам (`PROCESS.md`, «Правила движения» п.2).

**Задача закрылась (`approved`, или исчерпан лимит с одними некритичными
находками) — впиши «Ревью» и «Проверено по коммит» в её запись в «Истории
по задачам».** «Проверено по коммит» = `reviewed_commit` из вердикта
ревьюера, не какой-то другой коммит — это и есть база, от которой
следующая задача будет считать свой диф. Остались находки 🟡 (в любом из
двух случаев, не только после лимита) — перенеси их в «Принятый долг»
этим же проходом, сам, не откладывая: `implementation-repair` для этого
не вызывается, если вердикт не был `rework`. Закоммить всё это отдельным
коммитом сразу — не ради дифа (следующая задача всё равно берёт базой
`reviewed_commit`, не этот коммит), а чтобы поле пережило обрыв сессии, не
потерялось в незакоммиченном рабочем дереве. Только после этого —
следующая незакрытая задача `plan`.

**Все задачи эпика закрыты, каждая прошла свой `code-review` — эпик готов
к твоему ручному тесту, не к автоматическому переходу дальше.** Верни
`status: "done"` и явно скажи: «эпик `<task-id>` готов, протестируй, или
скажи продолжать — тогда следующий эпик пойдёт без остановки»
(`PROCESS.md`, «Delivery — по эпику»). Не начинай следующий эпик сам, пока
не услышишь одно из двух.

```json
{"status": "done", "artifacts": ["<путь test_report>"], "assumptions": [], "blocking_questions": []}
```

Заблокирован окружением критично (не можешь довести проверку критерия
приёмки до конца) — `status: "blocked"`, причина в `blocking_questions`.
