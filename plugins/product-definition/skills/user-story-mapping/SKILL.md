# User Story Mapping — три этапа Definition

Ты ведёшь владельца через весь Definition: путь пользователя → эпики и
скоуп → детальная проработка каждого эпика. Три этапа, всегда в этом
порядке, каждый со своим видом согласования.

Общайся на русском. Опирайся на бриф и персоны.

## Жёсткое ограничение: бизнес-версия карты

- **Не делай:** Technical Stories, Enabler Stories, tech-теги, упоминания
  фреймворков и архитектуры.
- **Делай:** User Stories (ценность для пользователя), System Stories,
  Backbone, детальные сценарии, эдж-кейсы. Технику добавит `architecture`.

## Этап A — путь целиком, стоп на подтверждение

Собери backbone из брифа и персон: верхнеуровневые шаги пути пользователя
слева направо. Найди слепые зоны, предложи их владельцу (2-4 вопроса за
раз, не «что ещё?» вслепую).

**Шаг backbone — то, что человек, действующий как пользователь, переживает
через сам продукт** (сообщение, экран, действие в интерфейсе), не разовая
настройка/конфигурация/контент, которые обсуждаются с тобой напрямую и не
проходят через интерфейс продукта. Легко перепутать на соло-продуктах, где
владелец и есть единственный пользователь — его работа с агентом по
конфигурации не становится шагом его пути только потому, что её делает тот
же человек.

Пример (личный Telegram-бот-дайджест, владелец = единственный пользователь):
- ❌ Настройка источников (список каналов/RSS) → Первый запуск → Приветствие
  → Дайджест — «Настройка источников» здесь не пережита пользователем через
  бота, а сделана владельцем в разговоре с агентом.
- ✅ Первый запуск бота → Приветственное сообщение → Ежедневный дайджест;
  источники — вход для истории «дайджест собирается из настроенных каналов»,
  не отдельный шаг backbone.

**Покажи backbone целиком, одним списком шагов, без эпиков и историй под
ним, и спроси прямо: «это весь путь, который должен попасть в
разработку?».** Жди явного подтверждения или правки — не продолжай на своё
усмотрение. Поправил — вернись к сбору для затронутых шагов, не переходи
к этапу B с несогласованным путём.

Запиши backbone в `story_map` сразу после подтверждения — до записи на
диск путь не считается согласованным.

## Этап B — эпики, скоуп, визуальный концепт, IA

Разложи путь на эпики (крупные куски функциональности под шагами backbone).
**По каждому эпику явно спроси владельца: в первый релиз или в `backlog`.**
Не общим согласием на весь список — по каждому эпику отдельно. То, что
уходит в `backlog`, пишется туда же плоским списком, без приоритета: сам
эпик и, если известно, поле «Зависит от».

**Каждому эпику, вошедшему в релиз, присвой `<task-id>` сразу здесь** —
короткий kebab-slug (`oplata-podpiski`), не позже (`PROCESS.md`,
«Реестр артефактов»). Впиши его же в поле «task-id» под заголовком эпика
в `story_map` (см. шаблон) — без этого сопоставление `EPIC-00X` ↔
`<task-id>` не записано нигде, и через полгода на эпике из `backlog` это
станет догадкой. Впиши список в `status.md` строкой «Скоуп релиза»,
рядом с номером эпика: `oplata-podpiski (EPIC-003)`. Дальше по цепочке
(`story-map-reviewer`, `epic-prep`) этот `<task-id>` только читают.

**Тут же — визуальный концепт и информационная архитектура, на весь
продукт целиком, не на релиз:**
- Визуальный концепт — если у продукта есть визуальный слой (сайт,
  приложение, бот с интерфейсом в чате). Платформа (Mobile/Desktop/оба) +
  2-4 фразы — настроение, референсы, принцип палитры, что исключено.
  **Обсуждением, не рисунком** — это не вайрфрейм. Спроси прямо, жди
  подтверждения. Запиши в `wireframes` разделом «Визуальный концепт» —
  этап C наследует его целиком (включая платформу), не переспрашивает.
  Продукт без визуального слоя (CLI, библиотека, фоновый сервис) — раздел
  пишется «не применимо, почему» (тот же приём, что в чек-листе брифа), не
  пропускается молча и не выдумывается для галочки.
- Информационная архитектура: если продукт больше одного-двух экранов,
  предложи `information-architecture` (или сделай сам разделом IA, если
  структура тривиальна) — sitemap, навигация, на весь продукт. Не жди
  запроса владельца, если эпиков больше двух — без общей структуры
  вайрфреймы этапа C по разным эпикам разъедутся по навигации.

**По завершении этапа B предложи владельцу сразу запустить
`architecture-design` (режим «Фундамент»)** — она идёт перед этапом C, не
рядом с ним (`PROCESS.md`, «Технический фундамент»). Не жди, что это
отдельным заходом заметит `orchestrate`.

## Этап C — эпик за эпиком, строго последовательно

**Не начинай первый эпик, пока фундамент не прошёл `architecture-review`.**
Эпики режутся и согласуются владельцем на этапе B независимо от
фундамента, но детальная проработка (истории, сценарии, вайрфреймы) на
него опирается — начинать раньше значит строить на непроверенном.

**Следующий эпик не начинается, пока текущий не согласован владельцем
целиком и не прошёл `story-map-review`.** Не параллель, не забегание
вперёд — продуктовая логика укладывается слоем за слоем.

Для каждого эпика скоупа, по порядку:

1. Разложи эпик на истории с детальным сценарием (не только AC — шаги,
   ветвления), эдж-кейсами (что если два действия одновременно, что если
   пусто/ошибка/лимит), разметкой.
2. Предложи вайрфреймы экранов этого эпика — держись визуального концепта
   и IA из этапа B, не переизобретай их.
3. **Покажи владельцу эпик целиком** (все истории и экраны этого эпика
   разом, не по одной) — он правит, добавляет, убирает по всему эпику.
4. Сохрани в `story_map`/`wireframes`.
5. Предложи гейт `story-map-review` **на этот эпик** (ревьюер — в таблице
   «Гейты», `PROCESS.md`); запусти именно `story-map-reviewer`, не
   `general-purpose`, веди лимит **1 ревью** (`PROCESS.md`, «Лимит
   циклов» — владелец уже согласовал эпик лично, до этого гейта), запиши
   вердикт сам (`PROCESS.md`, «Правила движения» п.2).
6. **Лёгкий чек фундамента** — не гейт, не отдельное ревью: прочитай
   `architecture` (фундамент) и сверь на глаз с только что принятым эпиком
   (истории, эдж-кейсы, вайрфреймы) — не появилось ли детали, которую
   фундамент не покрывает или которой прямо противоречит. Подозрение
   подтвердилось — не решай сам: строка в «Открытые вопросы» `status.md`,
   блокер класса Б (`PROCESS.md`, «Конфликт эпика с техническим
   фундаментом») — `epic-prep` формально сверит на своём шаге 1, но не
   должен узнавать об этом первым.
7. Только после этого — следующий эпик.

**Единица среза без критерия приёмки и сценария — не оставляй так**: это
значит, эпик не проработан до конца, а не то, что можно добрать на
`epic-prep` — тот шаг переводит уже готовое в техническую форму, не
дописывает продуктовую.

Правишь уже принятый эпик повторно (не первая запись) и на нём уже
что-то построено ниже по цепочке (архитектура эпика, задачи) — отметь в
«Открытые вопросы» `status.md` (`PROCESS.md`, «Правила движения» п.6;
условие и снятие — там же).

## Повторный прогон — детализация следующего скоупа

После `learn`, когда владелец выбрал новый скоуп (`PROCESS.md`, «Launch и
Learn») — не строй backbone заново. Путь (этап A) пересматривается только
если новый скоуп меняет его существенно — владелец решает явно, не по
умолчанию. Обычно сразу этап C для новых эпиков: подними нужные из
`backlog`, разложи на истории тем же порядком.

### Черновик — на диск после каждого шага

Пиши накопленное в `.process/story_map_draft.md` (класс `scratch`) после
этапа A, после этапа B, и после **каждого** согласованного эпика этапа C —
восстанавливать по памяти дороже, чем дописать в черновик.

## Режим в пайплайне (автономный)

Даже без диалога **стопы на подтверждение не отменяются** — владелец не в
диалоге, но backbone/скоуп/концепт/эпик построены без него, и это ровно то,
что может уйти в разработку незамеченным. На каждой точке (конец этапа A,
конец этапа B, конец каждого эпика этапа C) впиши в «Открытые вопросы»
`status.md` строку «[что именно] — ждёт подтверждения владельцем» и верни
`status: "blocked"` с тем же текстом в `blocking_questions`, не `"done"`.
Автономный режим экономит диалог по деталям, не сам факт согласования.

```json
{"status": "blocked", "artifacts": ["<путь story_map>"], "assumptions": [...], "blocking_questions": ["Backbone — ждёт подтверждения владельцем"]}
```

## Шаблон (`story_map`)

```markdown
# User Story Map: [Название продукта]

## Backbone (путь пользователя)
[Шаг 1] → [Шаг 2] → [Шаг 3] → [Шаг 4] → [Шаг 5]

## Эпик: [EPIC-001] Название
**Скоуп:** релиз 1 / backlog
**task-id:** [kebab-slug, если эпик в релизе — тот же, что в «Скоуп
релиза» status.md; пусто, если ещё в backlog]

### [US-001][Роль] Как [роль], я хочу [действие], чтобы [ценность].
**Сценарий:** [шаги, ветвления]
**Эдж-кейсы:** [что если …]
- [ ] AC 1
- [ ] AC 2

### [SS-001][Система] Как система, я хочу [действие], чтобы [ценность].
- [ ] AC 1

## Gap Analysis & Risks
- **Пропущенные функции:** …
- **Открытые вопросы:** …
- **Риски:** [⚠️ Risk] …
- **Принятый долг:** [заполняется при закрытии story-map-review, если
  остались некритичные находки после лимита циклов]
```

## Критерии качества (самопроверка)

- Backbone показан отдельно от деталей, подтверждён владельцем — не тихо
  принят по умолчанию.
- Скоуп решён по каждому эпику явно, не общим согласием.
- Визуальный концепт и IA согласованы на этапе B, не переспрашиваются на
  каждом эпике.
- Следующий эпик не начат, пока текущий не согласован и не прошёл гейт.
- Каждая история — со сценарием, эдж-кейсами, AC — не только заголовком.
- Нет технических/enabler-историй.
- В backbone нет шагов настройки/конфигурации/контента, которые владелец
  делает с агентом напрямую — тот же класс ошибки, что технические истории,
  только уровнем выше (backbone, не история).
