## Желаемый пользовательский путь

В каждом продуктовом проекте один основной чат оркестратора. Владелец ставит
цели и согласует конкретные пакеты в нём. Оркестратор готовит задание, выбирает
и объясняет модель/уровень рассуждения/роль исполнителя, затем в разрешённых
границах сам запускает отдельный рабочий контекст. После завершения получает
результат и статус, при необходимости проводит согласованное независимое ревью,
ведёт Git/PR и предъявляет итог владельцу. Владелец не переносит сообщения между
исполнителями вручную. На контрольной точке оркестратор останавливается.

В основном чате держать решения и краткие итоги; подробные логи/исследования
остаются у исполнителей и в отчётах. Оркестратор также может быть заменён новой
сессией: состояние и границы разрешения восстанавливаются из репозитория.

## Что требуется спроектировать и проверить

- Различить встроенных субагентов и обычные самостоятельные задачи приложения.
  Обосновать выбор для коротких подзадач и длительной работы; не обещать, что
  любой соседний чат автоматически вернёт результат без отслеживания.
- Описать разрешение на делегирование в карточке пакета, роли, доступные модели,
  ограничения расходов/повторов и точку остановки. Не запускать агентов только
  по наличию этого документа. Пользовательские задачи не создавать без прямого
  разрешения владельца; эти два новых чата он создаёт сам.
- Задание исполнителя: цель, входы/версии, разрешённые файлы и действия, DoD,
  проверки, модель, ветка/рабочая копия, способ вернуть результат.
- Возвращаемый итог: выполнено/нужен ответ/заблокировано/не прошло проверку,
  изменённые файлы/commit, доказательства, ограничения, оставшиеся вопросы.
- Защитить изменения от пересечения: один пишущий исполнитель по умолчанию;
  изоляция отдельных рабочих копий при реально нужной параллельной записи.
- Не выдавать самопроверку за независимое ревью. Не переносить допуск между
  изменившимися версиями и не принимать зелёное ревью за разрешение прод.
- Измерить чтение правил, токены/время и повторы. Простой пакет не обязан
  проходить все продуктовые методики. Не плодить дубли состояния и регламентов.

## Ближайший результат этой задачи

Представить владельцу компактный план и логику до реализации: конкретные
файлы изменений, роли/модели, проверки, DoD и стоп. Согласовать обновление P3:
первым предметным пилотом может стать аудит финансового приложения на чтение.
В новом чате приложения отдельно согласуются границы этого аудита; не считать
идею пилота разрешением менять продукт или личные данные.

После согласования реализовать минимальную механику и показать полный цикл
«задание → исполнитель → возвращённый итог → проверка → остановка», затем
восстановление основного чата. Проверки среды, роли и ограничения фиксировать
честно; не объявлять оркестрацию готовой по одним текстам инструкций.

Критерий готовности: владелец общается с оркестратором; исполнители получают
узкие задания; результат возвращается без ручного копирования; модели и
проверки понятны; checkpoint соблюдается; следующая сессия восстанавливается.

Это ТЗ и контекст для согласования. Реализация нового механизма, запуск
исполнителей, слияние PR и глобальная активация требуют соответствующего
разрешения в ближайшем конкретном пакете. Уже принятые P1/P2 повторно не согласовывать.
