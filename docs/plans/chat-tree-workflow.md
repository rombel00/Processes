# Дерево ограниченных задач: пакет 17.09.2026

Статус: реализация разрешена, результат предъявляется отдельно; приёмка не записана.
Родитель: codex-onboarding, P3 → ограниченное глобальное включение P4 после проверок.

## Основание и границы

Источник: текущая задача обсуждения Processes, сообщение Романа от 17.09.2026
после предложения «Что конкретно предлагаю изменить». Слова владельца:
«Хорошо делай все как считаешь нужным». Дополнение того же сообщения:
«Первый чат установочный как раз про постановку проекта. Далее все дальнейшие
этапы это так: первый чат по этапу для планирования, далее в отдельных чатах
делаются этапы этого плана. Получается такое дерево» и просьба процессу помнить,
останавливать и напоминать. Это запись действительного разрешения на предложенную
работу, не утверждение, что этот файл существовал до согласия или получил SHA-допуск P2.

Результат: единый цикл каждой задачи и сохранённая иерархия без нового менеджера
задач. Существующие продуктовые и инженерные методы остаются. Малая работа может
объединяться; разрешение родителя не наследуется детьми. На каждом DoD — STOP.

Разрешены: правки договора/шаблонов, orchestrate и Codex-входа, устранение
противоречий, компактная команда handoff, тестовые временные проекты,
независимое read-only ревью Astra, локальное глобальное включение после проверок.
Один пишущий исполнитель; один проход ревью, без повторных запусков без причины.
Файлы существующих продуктовых проектов, личная БД, платные интеграции,
prod/deploy, GitHub/push/merge и создание пользовательских задач не входят.
Коммит не выполняется этим пакетом; изменения предъявляются рабочим diff.

## План и DoD

1. Общий договор и шаблоны: узел/родитель, тип задачи, DoD, допуск, handoff/STOP.
2. Навыки: короткий универсальный вход; delivery-подробности по необходимости;
   Sol/Terra/Astra как политика ролей, без имитации переключения модели.
3. Runtime: read-only handoff поверх doctor; сохранность P2 и отказ при stale approval.
4. Проверки: автотесты, контракт skills, независимые сценарии в свежем контексте.
5. После успешных проверок: общий AGENTS и пользовательский process-entry,
   резервная копия, проверка нового запуска; старые подключения не обновлять молча.
6. Итог в [отчёте](../validation/chat-tree-workflow.md), инструкция использования и STOP.

Доказательства DoD: планирование не запускает детей; узел восстанавливается
без повторного интервью; новое пожелание требует карточки; личная БД не входит
в демо-допуск; handoff не меняет checkpoint; шаблоны не требуют полного цикла
для мелочи. Проверки не доказывают невозможность будущего отклонения модели.

## Передача после этого пакета

Следующий предлагаемый узел: реальный пилот в отдельной задаче финансового
приложения, Sol — планирование выбранного этапа. Его цель/DoD и границы сначала
обсуждаются там; этот пакет не разрешает аудит/разработку приложения.
Вернуться сюда нужно при дефекте самого процесса, с конкретным наблюдением.

После предъявления результата владелец расширил границы отдельным сообщением:
«Хорошо. Проанализируй на последок целостность процесса, может не хватает каких-то
важных этапов, описаний, что-то не сходится, где-то избыток. Короче финальный
анализ, шлифовка и мерж».

Это разрешает финальный аудит Processes, узкие исправления, независимый
read-only проход Astra, проверки, commit/push/PR и merge в main. Предыдущий
запрет Git-публикации выше относится к первому пакету, не к этому дополнению.
Принятый P2 (PR #17) сохраняется отдельным шагом истории перед новым PR.
DoD: противоречия разобраны, изменения проверены, оба PR слиты либо точно
назван внешний блокер, рабочее состояние проверено, владельцу передан итог.
Затем STOP: пилот приложения, его данные, платные сервисы и прод не входят.
