## Пользовательский путь

### Однократная настройка среды

Агент подготавливает доступ GitHub и подключение согласованной версии процесса. Владелец проходит официальный вход/2FA, если среда этого требует. После проверки адаптера общие инструкции подхватываются при новых задачах. Секреты в чат и репозиторий не передаются.

### Новый проект

1. Владелец открывает папку проекта и пишет цель обычными словами.
2. Процесс читает существующий контекст. Если проекта ещё нет — проводит короткое интервью: цель и ожидаемый результат, пользователи, текущее состояние, формат результата, данные/доступы, цена ошибки и ограничения.
3. Процесс представляет рекомендацию по модулям с причинами, карту этапов с DoD и ближайший пакет. Включает модель, необходимость нового чата, проверки и точку остановки.
4. Владелец подтверждает или корректирует предложение.
5. Агент сохраняет паспорт проекта, подключает согласованные модули и проверяет их доступность. Если нужен репозиторий, заранее указывает владельца, имя и видимость; создаёт/подключает его в рамках разрешённого пакета.
6. Работа идёт до согласованной контрольной точки. Подключённый модуль не является разрешением сразу выполнять все его этапы.

### Существующий проект

Прочитать инструкции и состояние, назвать текущий этап и границы разрешения. Повторять интервью только по отсутствующему или изменившемуся контексту. Не проводить весь Frame заново при каждой небольшой задаче.

## Как выбираются модули

| Модуль | Основание рекомендации |
| --- | --- |
| Общие рабочие правила | Всегда: согласования, DoD, остановки, вопросы, документация, прод |
| Исследование | Есть вопрос о рынке, пользователях или фактах, на который ещё нет надёжного ответа |
| Определение продукта | Создаётся продукт; нужно определить сценарии, ценность, границы и критерии успеха |
| Дизайн | Предстоят интерфейс или визуальное решение, которые надо предъявить владельцу |
| Технический модуль | Предстоит создание/изменение программного продукта, интеграции, схемы хранения, инфраструктуры или развёртывания |

Чувствительные данные повышают требования к проверкам, но не превращают любой аналитический документ в разработку ПО. Одноразовый скрипт не запускает полный продуктовый цикл только потому, что содержит код: процесс выясняет цену ошибки и предлагает соразмерный пакет. Общие правила сохраняются.

Это не три варианта глубины с разными копиями гейтов. Выбор предметных модулей и общие правила согласования описываются в одном месте. Для выбранного полного продуктового цикла действуют его согласованные гейты.

## Предлагаемые изменения P1 — контракт и маршрутизация

1. **Один общий контракт работы.** Короткие правила согласований, автономности внутри пакета, вопросов, ручного допуска в прод. Точка входа должна действовать и для задач вне полного продуктового процесса.
2. **Интервью и рекомендация модулей.** Описать один алгоритм выбора и паспорт проекта; разделить выбор модулей и разрешение на исполнение.
3. **Roadmap с DoD.** Добавить в реестр отдельную дорожную карту. Backlog сохраняет невыбранные идеи; PLAN хранит детали конкретного эпика, не дублирует roadmap.
4. **Версия согласования.** Отдельно хранить принятую логику, разрешённый пакет, контрольную точку, проверенную версию и разрешённую к выпуску версию.
5. **Выпуск.** Разделить readiness, согласие на конкретный commit/образ, deployment и последующую проверку. Включить обязательную проверку сводного ревью в перечень до выпуска.
6. **Согласование текстов.** Убрать противоречия README, PROCESS, orchestrate, launch-check и шаблонов. Сохранить исторические решения с указанием того, что заменено новым запросом владельца.

### Предполагаемые файлы P1

- plugins/process-core/PROCESS.md — реестр roadmap, переходы, состояния и допуск к выпуску.

- templates/ — шаблоны паспорта, roadmap и записи согласования; точное разбиение определить до правки.

### Definition of Done P1

- Для исследования, нового приложения и существующего проекта описан понятный путь входа без ручного выбора skills владельцем.
- Выбор технического модуля объясняется ответами интервью; неизвестное вызывает вопрос.
- Новая идея не запускает реализацию; прохождение ревью не означает согласия на прод.
- Есть отдельные roadmap/план эпика/состояние с непересекающимися обязанностями.
- Согласие на версию не переносится молча на изменившийся commit/образ.
- В существующих инструкциях не осталось маршрута, который противоречит этим правилам.
- Показаны diff и контрольные сценарии. Владелец принял новую редакцию. Публикация и установка ещё не выполняются.

Модель: GPT-6 Astra / high. По последнему согласованному предложению P1 выполняется в текущей задаче, одним исполнителем. Отдельное ревью/субагенты не запускаются. Самопроверка и три сценарных разбора описаны в [отчёте](../validation/p1-contract.md). Приёмка владельцем — после предъявления результата; агент её сам не отмечает.

## GitHub: что делает агент

В согласованном пакете: проверяет рабочее дерево, создаёт ветку, коммитит изменения, отправляет рабочую ветку и готовит PR. Проверяет существующие изменения и не включает их случайно в свой коммит. Слияние в тестовую ветку — по проектному контракту; конфликт смысла возвращает владельцу. Prod — отдельный допуск конкретной версии, даже если технически выпуск автоматизирован.

Первый вход в GitHub может требовать браузер и подтверждение аккаунта владельцем. После настройки владелец не должен вручную выполнять git checkout, push и команды создания PR. Коннектор GitHub и локальная авторизация Git проверяются отдельно.
