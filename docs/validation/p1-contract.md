## Метод проверки

Сценарный разбор выполнял тот же исполнитель: прочитал вход, прошёл новый
маршрут по инструкциям, проверил решение о модулях, нужные вопросы, документы
и границу остановки. Это самопроверка текста, **не независимое ревью и не
прогон установленного адаптера свежей моделью**. Примеры ниже учебные;
их «согласия» не являются разрешениями для реальных проектов.

## 1. Новое исследование

**Вход:** «Сравнить три ниши, результат — таблица спроса и конкурентов.
Разработки и сайта пока не нужно. Есть внутренние интервью с клиентами».

**Проход:**

1. Прочитать материалы, уточнить сами ниши, рынок/географию, период и способ
   принятия решения. Внутренние интервью не отправлять во внешние источники
   без разрешённого способа обработки.
2. Рекомендовать общие правила и product-discovery: есть исследовательский
   вопрос. Чувствительные интервью повышают требования к работе с данными,
   но не включают delivery. Product-definition/design не требуются только
   по факту слова «ниша».
3. Проверить обязательные входы выбранного market-research: нужен brief.
   Если его нет, предложить сначала согласовать исследовательскую постановку
   или иной самостоятельный метод исследования. Не создавать фиктивный бриф
   и не заявлять, что метод готов к запуску без обязательного входа.
4. Представить узкий пакет: вопросы, источники, проверка утверждений и таблица
   с ограничениями; DoD — три ниши по принятому набору критериев, ссылки и
   отличимые от фактов гипотезы. Модель и текущая задача — в карточке.
5. До согласия — только предложение. После отчёта — контрольная точка;
   код, репозиторий и инфраструктура не возникают автоматически.

**Результат:** маршрут не требует от владельца выбрать «полный процесс»;
цена ошибки и необходимость разработки разделены. Основание: договор 1–3,
orchestrate 0, реестр управляющих артефактов.

## 2. Новое приложение

**Вход:** «Семейный Telegram-бот и Mini App для финансов по скриншотам,
без доступа к банку; размещение на домашнем сервере».

**Проход:**

1. Восстановить известное, спросить отсутствующие роли/доступы, критерии
   распознавания, ограничения расходов, хранения и желаемый первый результат.
   Не придумывать модель денежных операций или аппаратную конфигурацию NAS.
2. Рекомендовать core + definition + design + delivery. Discovery добавлять
   под конкретный исследовательский вопрос, не обязательным исследованием рынка.
3. Roadmap: постановка/логика → мобильный дизайн → технический пакет → проверки
   интеграций → выпуск. У каждого этапа — работы, зависимости, DoD и стоп.
   Неизвестные числовые пороги сначала согласовать, а не считать выполненными.
4. Согласие на ближайшую постановку разрешает именно её. Приёмка макета или
   ревью не запускает разработку. Git выполняет агент в рамках принятой схемы.
5. Перед продом — отдельная версия/образ, окружение, доказательства и откат;
   после явного допуска сверка, выкладка, проверка фактически работающей версии.

**Результат:** технический модуль рекомендован из задачи без требования
технического выбора от владельца. Готовность/приёмка этапа/допуск продовой
версии различаются. Основание: договор 2–5, roadmap/package/approvals,
launch-check (включая сводное ревью, п.7).

## 3. Возврат в существующий проект

**Вход:** «Продолжим». В проекте прежний status, документы без нового паспорта,
незавершённая ветка и старое согласие на версию A; сейчас файлы версии B.

**Проход:**

1. Прочитать инструкции, документы, версии и фактический Git-статус. Старое
   поле «Масштаб процесса» — история, а не команда отключить или перестроить всё.
2. Сопоставить прежние документы с ID процесса, сохранить решения и ветку.
   Задать только вопросы, которых не хватает для определения разрешённого шага.
3. Если допуск текущего пакета действует и редакция соответствует — продолжить
   независимую разрешённую работу без повторного интервью и нового согласия
   на каждый коммит. Если остановились на ручной точке — предъявить следующий
   конкретный пакет; «продолжим» без ясного предмета не разрешает всё подряд.
4. Согласие A не разрешает выкладку B. Сравнить изменения и запросить новый
   допуск, не придумывать привязку старой отметки к текущему commit.
5. При смене задачи сохранить входы/версии/допуск/стоп. Создание новой задачи
   или команды агентов не вытекает из просьбы «продолжим».

**Результат:** работа восстановима без повторного полного Frame; переход
на новую структуру не стирает историю. Основание: договор 1, 3–5,
orchestrate 0–1 и handoff.

## Дополнительные проверки границ

| Ситуация | Проверенное решение по тексту |
| --- | --- |
| UI-прототип без разработки | Design/definition по задаче; фундамент delivery не требуется, если delivery не выбран |
| Короткий скрипт на тестовых данных | Узкий технический пакет с явными входами и проверками; полный цикл не включается только из-за кода |
| Нет ответов для brief, дана только idea | Сохранить известное, вернуть вопросы/blocked; не выдумывать сроки, аудиторию и критерии |
| Code-review approved, нет согласия на прод | Остановка до допуска, никакого merge с автодеплоем |
| Есть допуск A, CI готовит merge-коммит B | B сначала подготовить/проверить и согласовать либо выкладывать одобренный immutable-артефакт |
| После допуска изменён digest/конфигурация | Старый допуск не действует на новую версию/окружение |
| «Ожидает сводного ревью» не пусто | Readiness blocked до исправления; п.7 включён в предрелизные условия |
| Подключён модуль с агентами, их запуск не согласован | Не делегировать автоматически; предложить способ ревью в пакете |
| Выкладка дала сбой | Зафиксировать сбой; откат только в рамках допуска, иначе решение владельца |

При разборе исправлены оставшиеся противоречия: требование технического
фундамента для design-only, переход к следующему эпику сразу после ревью,
изменение продуктовой логики после visual-design без решения владельца,
передача Git-команд владельцу и догадки в автономном brief.
