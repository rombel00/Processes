# Проверка итерационной сборки крупного блока

Дата: 18.09.2026  
План: [`docs/plans/iterative-block-delivery.md`](../plans/iterative-block-delivery.md)

## Что проверено

- новый проект: A/B дают тонкий scope, затем создаётся фундамент, после чего
  первый подблок проходит C → impact → plan → implementation/integration;
- существующий проект: используется доверенный baseline и дельта фундамента,
  а не повторный полный аудит;
- подблок без триггеров/вопроса фиксирует
  `covered_by_foundation + local-no-trigger-check` без дорогого advisor;
- подблок с вопросом или триггером проходит read-only advisor, который может
  вернуть как `covered_by_foundation`, так и `delta_required`/`blocked`;
- только `delta_required` создаёт адресную архитектурную дельту и review;
- продуктовый/дизайн-маршрут без разработки проходит последовательные C без
  неприменимых foundation/impact/code-шагов;
- один delivery-пакет может последовательно закрывать несколько связанных
  подблоков; производные C/impact/delta/plan/code фиксируются после появления и
  не требуют переподписать неизменившийся пакет;
- первое сообщение проектной задачи обязано показать фактическую модель,
  рекомендуемую модель и причину; Terra — обычный ограниченный исполнитель,
  Sol — неоднозначность/интеграция, Astra — high-risk architecture/review.

## Независимое ревью

Read-only reviewer сначала вернул `rework` по четырём P2-стыкам:

1. handoff ошибочно превращал любой trigger в обязательную дельту;
2. пакет должен был заранее pin'ить ещё не созданные результаты итерации;
3. data-checklist требовал полную модель будущих подблоков уже в фундаменте;
4. маршрут «спецификация/дизайн без разработки» оказался заблокирован impact.

После исправлений reviewer дополнительно нашёл рассинхрон для консультации по
конкретному вопросу без формального trigger и устаревший regression regex.
Все находки исправлены. Финальный verdict: **approve**, оставшихся P1/P2 в
проверенных стыках нет; reviewer файлы не менял.
